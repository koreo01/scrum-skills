# PBI Template Story

check-story.md のチェックを通過しやすい Story チケットの雛形を出力します。

## コマンド形式

```
/pbi:template-story [--title "タイトル"]
```

| 引数 | 説明 |
|-----|------|
| `--title "タイトル"` | タイトルをあらかじめ埋めた状態で出力 |
| （省略） | 全フィールドが空欄の雛形を出力 |

---

## 使い方

> **議事録由来で作成する場合**: 先に `/pbi:invoke-story-ticket-helper` を実行してチケット候補を抽出してください。

1. このコマンドを実行すると、下記テンプレートを出力します
2. `[...]` で囲まれた部分を実際の内容に置き換えてください
3. 記載後に `/pbi:check-story` で品質確認してください

---

## 空・雨・傘における位置づけ

Story は「空・雨・傘」フレームワークの **傘（対応）を仕様として展開した層** です。

```text
空（事実）  ←── Needs「事実（空）」
雨（解釈）  ←── Needs「解釈（雨）」
     ↓ 解釈をもとに対応策を定義する
傘（対応）  ←── Requirement「解決内容」
     ↓ 傘（対応策）をユーザー視点の仕様として展開する ← ここが Story
Story       ←── 受け入れ条件（Gherkin形式）：傘を「誰が・何をしたら・どうなるか」で記述
```

**Storyの役割**: Requirementで決めた「何をするか（傘）」を、ユーザーが観察できる振る舞いとして具体化する。
Given/When/Then の各節はすべてユーザー視点で記述し、実装詳細（API・DB・内部処理）は含めない。

**エラーケースの扱い**: 同一の When（操作・トリガー）に対する異常応答は、同一 Story 内の S2 または Scenario Outline の Examples 行として網羅する。When が異なる別の操作は別 Story として起票する。判断の詳細は `check-story.md` の項目16・エラーケース分割の判断軸を参照。

## 出力テンプレート

以下のテンプレートをそのまま出力する：

```markdown
# [Storyタイトル]
<!-- Title形式: 「〇〇は△△できる」または「〇〇として、△△できる」-->
<!-- NG例: 「予約変更機能を実装する」（実装形式） / 「予約を変更したい」（願望形式） -->
[ユーザー]は[操作・機能]できる

## 元Requirement
<!-- 必須: 派生元Requirementの#xxxを記載 -->
【元Requirement】[#xxx または URL]

## 受け入れ条件

### パターン A: 単一シナリオ（1パターンのみの場合）
<!-- 1つの When に対して1つの結果のみの場合 -->
Given: [前提条件]
  - [条件1: ログイン済み・画面表示中など]
  - [条件2]
When: [ユーザーの操作（「〜ボタンを押す」「〜を入力する」等）]
Then:
  - [期待結果1: ユーザーが観察できる結果]
  - [期待結果2]
  <!-- NG: 「DBが更新される」「APIが呼ばれる」（実装詳細） -->
  <!-- OK: 「〜が表示される」「〜に変更される」「メールが届く」 -->

### パターン B: Scenario Outline（複数パターンを網羅する場合）← デフォルト推奨
<!-- 同一の When に対して正常系・異常系・境界値を Examples テーブルで一元管理する -->
<!-- Scenario Outline を使う場合、Examples テーブルは必須（check-story.md #11） -->
Given: [共通の前提条件]
When: [ユーザーの操作（全パターンで同一）]（<[変数名]>）
Then: <[期待結果の変数名]>

Examples:
| [変数名]  | [期待結果の変数名]              |
| [正常系値] | [具体的な成功メッセージ・状態]   |
| [異常系値] | [具体的なエラーメッセージ・状態] |
| [境界値]   | [具体的なメッセージ・状態]      |
<!-- Examples は 5件以下が目安。6件以上の場合は「仮説の境界」でスプリット検討を推奨（#18）。件数ではなく同じ When で検証できるかで判断する -->

## 検証スコープ（推奨）
<!-- check-story.md #17 に対応。試すパターン・試さないパターンを宣言してスコープの境界を明示する -->
【検証スコープ】
- 試す: [パターン名（件数）]、[パターン名（件数）]
- 試さない: [パターン名]（[除外理由・対応予定]）

## SubTask候補（任意）
- [ ] [SubTask1]
- [ ] [SubTask2]
```

## Refinement で必ず行うこと

このテンプレートに書き込む前に、Refinement で以下を済ませる:

1. **Example Mapping**: 具体的な入力値・期待値の組み合わせを最低3パターン整理する
   （正常系1、異常系1、境界値1 を目安）
2. **試さないパターンの宣言**: スコープ外にするケースを明示する
3. **When の統一性確認**: 全シナリオが同一のトリガー（操作）を指していることを確認する。
   異なる When がある場合は別 Story に分ける（check-story.md 項目16・エラーケース分割の判断軸 Layer 1 参照）

Refinement が不十分なまま Story を起票すると、SubTask 分解と受け入れの工数が人によって大幅にぶれる（本ガイドの中心的な問題意識）。

## よくある記載ミス

| ミスのパターン | 正しい書き方 |
|-------------|------------|
| Then: `DBのXXXテーブルが更新される` | Then: `〜が反映される`（ユーザー視点に） |
| Then: `PUT /reservations/{id} が呼ばれる` | SubTaskに記載。ACには書かない |
| Then: `正しく更新される` | 具体的な状態（`予約日時が〇〇に変わる`等） |
| Then: `適切にエラーが表示される` | 表示されるメッセージを具体的に記載 |
| Scenario Outline の Examples に異常系行がない | 同一 When への異常応答は Examples 行として記載する（check-story.md #8） |
| Scenario Outline で Examples なし | `Examples:` テーブルを必ず追加（#11 で ❌） |
| Examples の値が変数名のみ（`<value>` 等） | 具体的な入力値・期待値を記載（#11 で ❌） |
| 検証スコープが未宣言 | `【検証スコープ】` セクションを追加（#17 で ⚠️） |
| Examples が 6件以上で無条件スプリット | 「仮説の境界」で判断する。同一 When なら件数が多くても同一Story内に留める（#18） |
