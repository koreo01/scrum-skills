# PBI Check Bug Agent

Bugチケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-bug [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/bug-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のBugチケットをチェック
/pbi:check-bug #123

# チェック結果をファイルに保存
/pbi:check-bug #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-bug #123 --gh-comment

# 対話モード
/pbi:check-bug
```

## Bug Issue の特徴

Bug Issueは**不具合・異常動作**を報告するIssueです。

### Title/Summary のパターン

| パターン | 例 |
|---------|-----|
| 〇〇が正常に動かない | 「ログインボタンが正常に動かない」 |
| △△でエラーが発生 | 「PDF出力でエラーが発生」 |
| 🔳🔳が表示されない | 「ダッシュボードのグラフが表示されない」 |
| ××すると落ちる | 「動画をアップロードすると落ちる」 |

### Needs/Tech との違い

| 観点 | Needs | Tech | Bug |
|------|-------|------|-----|
| 起点 | 顧客の要望 | 開発者の課題認識 | 動作不良の発見 |
| Title形式 | 「〇〇したい」 | 「〇〇がやりづらい」 | 「〇〇が動かない」 |
| 必須情報 | 背景・解釈 | 背景・定量データ | **再現手順・環境** |

## Statusライフサイクル・Owner

### Statusライフサイクル

| Status | 意味 | Ownerの目安 |
|--------|------|------------|
| Triage | 調査・判断待ち | Business |
| Refining | Refinement中 | Business |
| Story Defined | Story / Task 起票済み | Product |
| In Sprint | 対応作業中 | Product |
| Done | 完了 | Product |

### Owner

| タイミング | Owner |
|-----------|-------|
| 起票〜Refining | Business |
| Story Defined以降 | Product |

## チェック対象テンプレート

### 事実テンプレート（Bug用）

| 種類 | フォーマット | Bug Issueでの例 |
|------|------------|-----------------|
| **記録** | `[いつ]、[システム/ツール名] に [こう記録されている]。` | 「4/1 10:00、エラーログに NullPointerException と記録されている。」 |
| **直接の発言** | `[いつ・どこで]、[誰] が [こう言った/書いた]。` | 「今朝、CS担当の山田さんが『顧客からログインできないと連絡があった』と言った。」 |
| **観察** | `[いつ・どこで]、私は [こうなっているの] を見た/聞いた。` | 「4/1 9:30、私はログインボタンをクリックしても画面が遷移しないのを見た。」 |

### 解釈テンプレート

```
[この事実] から、[こういう意味だ] と私は読んでいる。
なぜなら [この事実] と [別の知識・事実・経験] を結びつけているからだ。
（ただし [別の結びつけ方] もありうる。）
```

### Bug固有: 再現情報テンプレート

```
【再現手順】
1. [操作1]
2. [操作2]
3. [操作3]

【環境】
- OS: [OS名とバージョン]
- ブラウザ: [ブラウザ名とバージョン]
- ユーザー種別: [管理者/一般ユーザー等]

【期待動作】
[本来こうなるべき]

【実際動作】
[実際にはこうなった]
```

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Triage / Refining / Story Defined / In Sprint / Done のいずれか |
| 0-2 | Ownerの設定 | Business または Product が設定されている |
| 0-3 | Owner×Statusの整合 | Triage・Refining は Business、Story Defined 以降は Product |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | 事実セクション存在 | 「事実」または観察・記録の記載がある |
| 2 | 再現手順の存在 | 「再現手順」「手順」「Steps」等がある |
| 3 | 環境情報の存在 | 「環境」「OS」「ブラウザ」等の記載がある |

### Phase 2: フォーマット準拠チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | Title形式 | 不具合形式（「〇〇が動かない」「エラー発生」等） |
| 5 | 再現手順が番号付き | 1. 2. 3. のように順序が明確 |
| 6 | 期待動作の記載 | 「期待」「本来」「あるべき」等の記載 |
| 7 | 実際動作の記載 | 「実際」「結果」「発生した」等の記載 |
| 8 | 時間情報の具体性 | 発生日時が具体的に記載されている |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 9 | 再現率の記載 | 「常に」「時々」「特定条件で」等 |
| 10 | エビデンスの有無 | スクリーンショット、ログ、動画等 |
| 11 | 影響範囲の記載 | どのユーザー/機能に影響するか |
| 12 | 発生メカニズムの推測 | 原因の仮説があれば記載（任意） |

## 出力ファイル

### `--save` オプション使用時

出力先: `analysis/format-check/YYYY-MM-DD_<ticket-id>.md`

```markdown
# フォーマットチェック結果

- **チケット**: BUG-456「ログインボタンが動かない」
- **チェック日時**: 2026-04-01 21:00
- **スコア**: 75/100（⚠️ 要改善）

## 指摘事項

### ⚠️ 環境情報が不完全
- 箇所: 環境セクション
- 現在の記載: `Chrome で発生`
- 対応: OS、ブラウザバージョンを追記

### ❌ エビデンスなし
- 対応: スクリーンショットまたはエラーログを添付

## 次のアクション

1. [ ] 環境情報を詳細に記載
2. [ ] エビデンスを添付
3. [ ] 修正後に再度 `/pbi:check-bug` で確認
```

### `--gh-comment` オプション使用時

GitHub Issue のコメントに以下が追記されます：

```
📋 フォーマットチェック結果（2026-04-01）
スコア: 75/100（⚠️ 要改善）

【指摘事項】
⚠️ 環境情報が不完全: OS、ブラウザバージョンを追記してください
❌ エビデンスなし: スクリーンショットまたはログを添付してください

修正後に再度チェックをお願いします。
```

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ 不具合形式 | `〜が動かない`, `〜できない`, `エラー`, `〜が表示されない`, `〜すると落ちる`, `〜が消える` |
| ❌ 願望形式 | `〜したい`, `〜できるとよい`（→ Needsの可能性） |
| ❌ 課題形式 | `〜がやりづらい`, `〜に時間がかかる`（→ Techの可能性） |

### 再現手順の判定

| 判定 | パターン |
|------|---------|
| ✅ 良好 | 番号付きで3ステップ以上 |
| ⚠️ 不十分 | 番号なし、または1-2ステップのみ |
| ❌ なし | 再現手順の記載がない |

### 環境情報の判定

| 判定 | 含まれる情報 |
|------|------------|
| ✅ 完全 | OS + ブラウザ + バージョン |
| ⚠️ 不完全 | 一部のみ記載 |
| ❌ なし | 環境情報の記載がない |

### 再現率の判定

| 判定 | パターン |
|------|---------|
| ✅ 明確 | `常に`, `100%`, `毎回`, `必ず` |
| ⚠️ 条件付き | `時々`, `特定条件で`, `〜の場合のみ` |
| ❌ 不明 | 再現率の記載がない |

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 20点 | Status有効値・Owner設定・Owner×Status整合 |
| 構造チェック | 25点 | 事実・再現手順・環境の存在 |
| フォーマット準拠 | 30点 | テンプレート形式への準拠度 |
| 品質チェック | 25点 | 再現率・エビデンス・影響範囲 |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | 調査・修正に着手可能 |
| 60-79 | ⚠️ 要改善 | 指摘箇所を修正してから着手 |
| 0-59 | ❌ 要リライト | テンプレートに沿って書き直し |

---

## 注意事項

- このAgentは**フォーマット準拠**を主眼としています
- バグの原因特定や修正方法は判定しません
- 再現手順と環境情報は**必須**です（これがないと調査できない）
- エビデンス（スクリーンショット/ログ）は**強く推奨**です
- Title形式が「願望形式」や「課題形式」の場合、Issue Type変更を提案します
