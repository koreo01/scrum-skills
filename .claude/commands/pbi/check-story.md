# PBI Check Story Agent

Story（Requirement Specification）チケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-story [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/story-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のStoryチケットをチェック
/pbi:check-story #123

# チェック結果をファイルに保存
/pbi:check-story #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-story #123 --gh-comment

# 対話モード
/pbi:check-story
```

## 空・雨・傘における位置づけ

Story は「空・雨・傘」フレームワークの **傘（対応）を仕様として展開** する層です。

```text
空（事実）  ←── Needs「事実（空）」：観察・発言・記録などの生データ
     ↓ 事実をもとに意味を読み取る
雨（解釈）  ←── Needs「解釈（雨）」：事実から何を読み取るかの推論
     ↓ 解釈をもとに対応策を定義する
傘（対応）  ←── Requirement「解決内容」：雨（解釈）への具体的な対応策
     ↓ 対応策をユーザー視点の仕様として展開する ← ここが Story
Story       ←── 受け入れ条件（Gherkin形式）：傘（対応）の「誰が・何をできるか」
```

**Storyの役割**: Requirement の傘（対応）を受けて「**ユーザーは何ができるようになるか（仕様）**」を定義する。
What（傘の方向性）から What Specified（傘の仕様展開）へ翻訳する層です。

## Story (Requirement Specification) の位置づけ

```
Issue (Why)                    Requirement              Story (What Specified)
┌─────────┐                   ┌─────────────┐         ┌─────────────────────┐
│  Tech   │──(仕様変更あり)──→│             │────────→│ Story               │
│  Needs  │──(仕様変更あり)──→│ Requirement │         │ (Requirement Spec)  │
│  Bug    │──────────────────→│             │         │   ├── SubTask       │
└─────────┘                   └─────────────┘         │   ├── SubTask       │
                                                       │   └── SubTask       │
                                                       └─────────────────────┘
```

**Story** = 「要件から導き出された **仕様**」 = Requirement Specification

### Statusライフサイクル

StoryのStatusは以下の値のみが有効。他のIssue Type（Tech/Needs/Bug等）が持つTriageやRefiningはStoryには存在しない。

```
Story Defined → In Sprint → Done
```

| Status | 意味 | Owner目安 |
|--------|------|----------|
| Story Defined | Story作成・スプリント投入待ち | Product |
| In Sprint | スプリント中 | Product |
| Done | 完了・Released後も含む | Product |

### Workflow State

Story / Task / SubTask のみが持つプロパティ。スクラムチームの作業状態を表す（Issueには存在しない）。

| Workflow State | 意味 |
|---------------|------|
| Backlog | バックログに積まれた状態 |
| Sprint Ready | スプリント投入準備完了 |
| In Sprint Backlog | スプリントバックログに追加済み |
| In Progress | 作業中 |
| In Review | レビュー中 |
| In QA | QA中 |
| Done | 完了 |
| Released | リリース済み |

### Planned Release Version / Released Version

| プロパティ | 設定タイミング | 必須度 |
|-----------|-------------|-------|
| Planned Release Version | Status が In Sprint になった時点（スプリント投入時） | ⭐ 必須 |
| Released Version | Status が Done になり、リリースが完了した時点 | ⭐ Done後必須 |

### GherkinにおけるHow可否の境界

Story（Requirement Specification）の受け入れ条件は「What Specified」の層。
**システムの振る舞い**としてのHowは記載してよいが、**設計仕様**としてのHowはNG。

| 分類 | 可否 | 例 |
|------|------|-----|
| システムの振る舞い（ユーザー視点） | ✅ OK | 「予約日時が更新される」「エラーメッセージが表示される」「確認メールが届く」 |
| 設計仕様（実装・インフラ視点） | ❌ NG | 「PUT /reservations/{id} を呼び出す」「DBのreservationsテーブルが更新される」「APIを使って取得する」 |

> 判断軸: **ユーザー（またはPO）が観察・確認できる結果か？** → YesならOK、Noなら設計仕様

### Title/Summary のパターン

| パターン | 例 |
|---------|-----|
| 〇〇は△△できる | 「ユーザーはWeb画面から予約日時を変更できる」 |
| 〇〇として、△△できる | 「管理者として、ユーザー一覧をCSV出力できる」 |

### 他のIssue Typeとの違い

| 観点 | Needs | Requirement | **Story** |
|------|-------|-------------|-----------|
| **空・雨・傘** | 空（事実）＋雨（解釈） | 傘（対応の方向性） | **傘（対応の仕様展開）** |
| 起点 | 顧客の要望 | Issue分析の結果 | **Requirement分解の結果** |
| Title形式 | 「〇〇したい」 | 「〇〇を解決したい」 | **「〇〇は△△できる」** |
| 必須情報 | 背景・解釈 | 元Issue・解決内容 | **受け入れ条件（Gherkin）** |
| 抽象度 | Why（なぜ困っている） | What（何を解決する） | **What Specified（具体的にどう動く）** |
| 実装可能性 | × | △ | **◎（SubTaskに分解可能）** |

## エラーケース分割の判断軸

Story の正常系/異常系を別 Story に切り出すべきか、同一 Story 内の S1/S2 として扱うべきかは以下の3層で判断する。

### Layer 1: トリガー（When句）の同一性

- 同一トリガー → 同一 Story 内の S1/S2（同じ振る舞いに対する異なる応答）
- 異なるトリガー → 別 Story（項目16参照）

### Layer 2: 振る舞いの質的差異

同一トリガーでも応答が質的に大きく異なる場合は別 Story を検討する。

- 例: 「ログインボタン押下」に対して
  - 正常系: ダッシュボードへ遷移 → S1
  - パスワード誤り: エラー表示 → S2（同一 Story）
  - 3回連続誤り: アカウントロック+メール通知 → **別 Story 候補**（処理が質的に異なる）

### Layer 3: Sprint 内完走可能性

Layer 1/2 で同一 Story と判断しても、具体例(Examples)をすべて書き出した結果として Sprint 内で開発から受け入れまで完走できないサイズなら分割する。
項目18（Examples 5件ルール）はこの観点での目安。

**判断の出発点は「Sprint 内完走」**であり、INVEST の Independent/Valuable を理由に分割を躊躇しない。エラーケース単位での価値は運用・セキュリティ・ユーザビリティの観点で十分再確認されたい。

> 縦スライス分割の詳細は `/pbi:slice-story` および ai-driven-development-style-guide §3.3 を参照

## チェック対象テンプレート（スライド#10準拠）

### Storyの必須要素

| フィールド | 必須事項 | 例 |
|-----------|---------|-----|
| **Title** | 「〇〇は△△できる」形式（ユーザーストーリー形式） | 「ユーザーはWeb画面から予約日時を変更できる」 |
| **元Requirement** | 派生元Requirementへのリンク | 【元Requirement】#xxx |
| **受け入れ条件** | **Gherkin形式**で記載 | Given/When/Then |

### Title形式（ユーザーストーリー形式）

```
【推奨形式】
〇〇は△△できる

【詳細形式】
〇〇として、△△したい。なぜなら🔳🔳だからだ。
（As a [role], I want [feature], so that [benefit]）
```

### 受け入れ条件テンプレート（Gherkin形式 必須）

```gherkin
# パターン A: 単一シナリオ（1パターンのみの場合）
Given: [前提条件]
  - [条件1]
  - [条件2]
When: [操作・アクション]
Then: [期待結果]
  - [結果1]
  - [結果2]

# パターン B: Scenario Outline（複数パターンを網羅する場合）← デフォルト推奨
# 同一の When に対して正常系・異常系・境界値を Examples テーブルで一元管理する
Scenario Outline: [シナリオ名]
  Given: [前提条件]
  When: [操作・アクション（全パターンで同一）]
  Then: <expected_result>

  Examples:
  | [パラメータ1]  | expected_result                |
  | [正常系具体値] | [具体的な成功メッセージ・状態]  |
  | [異常系具体値] | [具体的なエラーメッセージ・状態] |
  | [境界値]       | [具体的なメッセージ・状態]       |
```

### SubTask分解の観点（任意）

```
【SubTask候補】
- [ ] フロントエンド: 予約変更画面の実装
- [ ] バックエンド: 予約変更APIの実装
- [ ] テスト: E2Eテストの追加
```

## チェックルール

### Phase 0: プロパティチェック

GitHub Issue のラベル（Status / Workflow State / Release Version / Mock Type）の設定が正しいかを確認する。

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Story Defined / In Sprint / Done のいずれか |
| 0-2 | Workflow Stateの有効値 | Backlog / Sprint Ready / In Sprint Backlog / In Progress / In Review / In QA / Done / Released のいずれか |
| 0-3 | Planned Release Versionの設定 | Status が In Sprint 以降の場合、必須設定されている |
| 0-4 | Released Versionの設定 | Status が Done の場合、設定されている（または未リリースであれば⚠️） |
| 0-5 | Mock Type の設定 | Vision / Sales / Build / N-A のいずれかが設定されている（必須）。未設定の場合は❌ |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | Title形式 | 「〇〇は△△できる」形式（ユーザーストーリー形式） |
| 2 | 元Requirementリンク | Requirementへのリンクまたは参照がある |
| 3 | 受け入れ条件の存在 | Gherkin形式の記載がある |

### Phase 2: Gherkin形式チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | Given節の存在 | 前提条件が記載されている |
| 5 | When節の存在 | 操作・アクションが記載されている |
| 6 | Then節の存在 | 期待結果が記載されている |
| 7 | シナリオの網羅性 | 正常系が最低1つある |
| 8 | 異常系の考慮 | 異常系パターンの有無（推奨）。Scenario Outline を使用する場合は Examples テーブルに異常系行が含まれているか。同一 When への異常応答は別シナリオではなく Examples 行として記載する |
| 9 | 設計仕様混入なし | Given/When/Then節にAPI・DB・実装詳細が混入していない |
| 10 | Scenario Outline の使用 | 複数パターンを検証する場合、Scenario Outline + Examples テーブルを使用している（Scenario Outline の場合は必須、単一シナリオは推奨） |
| 11 | Examples の具体性 | Scenario Outline がある場合、Examples テーブルに具体的な入力値・期待値が記載されている |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 12 | 検証可能性 | 各Then節が客観的に判定可能 |
| 13 | 具体性 | 曖昧な表現（「適切に」「正しく」等）がなく、Then 節の各条件が具体値（具体的なメッセージ文・具体的な状態・具体的な数値）で記載されている |
| 14 | SubTask分解可能性 | このStoryからSubTaskに分解可能か |
| 15 | 単一責任 | 1つのStoryが1つの機能に対応 |
| 16 | When句の一貫性 | 複数シナリオのWhen句がすべて同一の振る舞い（操作・トリガー）を指している。When句が2種類以上ある場合は振る舞いが混在しているため、When句ごとに別Storyへの分割を促す |
| 17 | 検証スコープの宣言 | 【検証スコープ】セクションに「試すパターン」と「試さないパターン」が明示されている（推奨）。記載がない場合は⚠️（推奨）、記載はあるが具体性・境界が不明な場合は⚠️（改善推奨）として指摘する |
| 18 | Examples 件数とスプリット判断 | Scenario Outline の Examples テーブルが 5件以下が目安。6件以上の場合は仮説の境界によるスプリットの検討を⚠️（推奨）として指摘する。ただし同一仮説のパターンなら件数が多くても同一Story内に留める |

## パターン検出ルール

### Mock Type の判定

| 判定 | パターン |
|------|---------|
| ✅ 設定済み | Vision / Sales / Build / N-A のいずれかが設定されている |
| ❌ 未設定 | Mock Type が未設定（空値） |

**各値の意味と運用ルール:**

| 値 | 用途 | Fidelity 上限 |
| --- | --- | --- |
| `Vision` | 投資家・社内向け概念説明 | L2 で止める（L3 は作らない） |
| `Sales` | 顧客説明・営業向けデモ | L1 で止める（L2 以上は作らない） |
| `Build` | 開発向け仕様・社内実装 | L1 → L2 → L3 まで段階的に進める |
| `N-A` | 画面開発を含まない Story | モック不要（バックエンドのみ等） |

**Mock Type 未設定時の表示メッセージ:**

```text
❌ Mock Type: 未設定

   Story には Mock Type の設定が必須です。以下から選択してください:
   - Vision: 投資家・社内向け概念説明（Fidelity 上限: L2）
   - Sales: 顧客説明・営業向けデモ（Fidelity 上限: L1）
   - Build: 開発向け仕様・社内実装（Fidelity 上限: L3）
   - N-A: 画面開発を含まない Story（バックエンドのみ等）
```

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ ユーザーストーリー形式 | `〇〇は△△できる`, `〇〇として、△△できる`, `As a ... I can ...` |
| ❌ 願望形式 | `〜したい`, `〜できるとよい`（→ Needsの可能性） |
| ❌ 解決意図形式 | `〜を解決したい`（→ Requirementの可能性） |
| ❌ 実装形式 | `〜を実装する`, `〜APIを作成`（→ SubTask/Howの可能性） |

### Gherkin形式の判定

| 判定 | パターン |
|------|---------|
| ✅ 完全 | Given + When + Then がすべて揃っている |
| ⚠️ 不完全 | 一部の節が欠けている |
| ❌ なし | Gherkin形式の記載がない |

### Given節の判定

| 判定 | パターン |
|------|---------|
| ✅ 具体的 | 状態・条件が明確（「ユーザーがログイン済み」等） |
| ⚠️ 曖昧 | 「準備ができている」等 |
| ❌ なし | Given節がない |

### When節の判定

| 判定 | パターン |
|------|---------|
| ✅ 具体的 | 操作が明確（「〜ボタンを押す」「〜を入力する」等） |
| ⚠️ 曖昧 | 「操作する」「実行する」等 |
| ❌ なし | When節がない |

### Then節の判定

| 判定 | パターン |
|------|---------|
| ✅ 検証可能 | 客観的に判定可能な結果（「〜が表示される」「〜件取得できる」等） |
| ⚠️ 曖昧 | `正しく`, `適切に`, `問題なく` 等の主観的表現 |
| ❌ なし | Then節がない |

### 曖昧表現の検出

| 検出パターン | 改善例 |
|-------------|--------|
| `正しく〜される` | 具体的な状態を記載 |
| `適切に〜する` | 具体的な動作を記載 |
| `問題なく〜` | 成功条件を具体的に記載 |
| `きちんと〜` | 判定可能な条件を記載 |
| `うまく〜` | 期待値を明示 |
| `不正な入力` | 「空文字列」「10000文字超」「全角英数字以外の入力」など具体的に |
| `エラーメッセージが表示される` | 表示されるメッセージ文を具体的に記載 |
| `その場合`（条件が抽象的） | 具体的な境界値・パターンを明示 |

### Scenario Outline + Examples テーブルの判定

複数パターンの検証が必要なシナリオ（Scenario Outline）の場合に適用する。

| 判定 | パターン | 対応 |
|------|---------|------|
| ✅ 使用・具体的 | Scenario Outline を使用し、Examples テーブルに具体的な入力値・期待値がある | そのまま OK |
| ⚠️ 推奨 | 複数パターンが文章またはシナリオの繰り返しで列挙されているが、Scenario Outline を使っていない | Scenario Outline への書き換えを推奨 |
| ❌ Examples なし | Scenario Outline を使用しているが、Examples テーブルがない | Examples テーブルの追加が必須 |
| ❌ Examples 抽象的 | Examples テーブルはあるが、変数名のみで具体値が記載されていない | 具体的な入力値・期待値への修正が必要 |

**単一シナリオ（Scenario Outline を使用しない場合）の扱い**:

- Examples テーブルはオプション（推奨）
- 異常系シナリオを別シナリオとして記載している場合は、Scenario Outline への統合を推奨

### When句の一貫性チェック

複数シナリオのWhen句を比較し、同一の振る舞い（操作・トリガー）を指しているかを判定する。

| 判定 | パターン | 対応 |
|------|---------|------|
| ✅ 一貫 | 全シナリオのWhen句が同一の振る舞いを指している（例：正常系・異常系ともに「ユーザーが〜ボタンを押す」） | そのままS1/S2として同一Storyで実装可 |
| ❌ 混在 | When句が2種類以上あり、異なる振る舞い（操作・トリガー）が混在している | When句ごとに別Storyへ分割を促す |

**When句が混在している場合の分割提案フォーマット**：

```
⚠️ 振る舞いの混在を検出しました。

以下のWhen句が異なる振る舞いを表しています：
- When: [振る舞い①] → Story A として分離を推奨
- When: [振る舞い②] → Story B として分離を推奨

異常系（S2）は同一When句内の追加ケースとして実装します。
When句が異なる場合は別の振る舞い＝別Storyです。
```

### 検証スコープの判定

【検証スコープ】セクションの存在と内容を評価する。

| 判定 | パターン | 対応 |
|------|---------|------|
| ✅ 明示的 | 「試すパターン」と「試さないパターン」が具体的に列挙されている | そのまま OK |
| ⚠️ 未宣言 | 【検証スコープ】セクションが存在しない | セクションの追加を推奨（⚠️） |
| ⚠️ 境界不明 | セクションはあるが「〜など」「〜に関連するもの」等、スコープの境界が曖昧 | 具体的なパターンと除外理由の記載を推奨（⚠️） |

**理想的な検証スコープの記載形式**:

```text
【検証スコープ】
- 試す: [パターン名（件数）]、[パターン名（件数）]
- 試さない: [パターン名]（[除外理由・対応予定]）
```

記載例:

```text
【検証スコープ】
- 試す: 住所変更（3パターン）、電話番号変更（3パターン）
- 試さない: 契約内容変更・マークスクリップの構造変更（次スプリント以降）
```

**スコープのスプリット判断基準**:

スプリット（別Storyへ分割）は件数ではなく「仮説の境界」で判断する。
同一の仮説（同じWhenで検証できる）であれば、パターンが多くても同一Story内に留める。

### Examples 件数の判定

Scenario Outline の Examples テーブル件数を評価する。

| 判定 | パターン | 対応 |
|------|---------|------|
| ✅ 適切 | Examples 5件以下 | そのまま OK |
| ⚠️ 件数過多 | Examples 6件以上 | 仮説の境界によるスプリット検討を推奨（⚠️） |

**判断の注意点**:

件数のみでスプリットを判断してはならない。以下の問いで仮説の境界を確認する。

1. これらのパターンはすべて同一の When（振る舞い）で検証できるか？
2. 同一仮説のバリエーション（入力値の違い）であれば、件数が多くても同一Story内に留める
3. When句が異なる別仮説であれば、別Storyへの分割を推奨

**件数過多時の表示メッセージ例**:

```text
⚠️ Examples 件数: N件（Scenario Outline 1件）

   Examples が5件を超えています（N件）。件数の多さは複数の仮説が混在しているサインである可能性があります。

   確認してください:
   - これらのパターンは同一の「When（振る舞い）」で検証できますか？
   - 同一仮説のバリエーションなら、このまま留める（件数では分割しない）
   - When句が異なる別仮説であれば、別Storyへの分割を推奨

   💡 スプリット判断の基準は「件数」ではなく「仮説の境界」です。
```

### 設計仕様混入の検出（Gherkin内）

| 検出パターン | 理由 | 改善例 |
|-------------|------|--------|
| `APIを呼び出す`, `APIを使って` | 実装詳細（How） | 「〜が取得できる」に置き換え |
| `PUT /`, `POST /`, `GET /` などのエンドポイント | 設計仕様 | エンドポイントはSubTaskに記載 |
| `DBに保存される`, `テーブルが更新される` | インフラ詳細 | 「〜が反映される」等ユーザー視点に |
| `バックエンドが〜を処理する` | 内部処理の記述 | 観察可能な結果のみ記載 |

## 良い例・悪い例

### 良い例 ✅

```markdown
# Title
ユーザーはWeb画面から予約日時を変更できる

# 元Requirement
【元Requirement】#xxx「予約変更をWeb完結できるようにしたい」

# 受け入れ条件

## Scenario Outline: 予約日時変更の可否検証
Given: ユーザーが予約詳細画面を表示している
  - ユーザーはログイン済み
When: ユーザーが新しい日付を選択し「更新」ボタンを押す（チェックイン <hours_remaining> 時間前）
Then: <expected_result>

Examples:
| hours_remaining | expected_result                                                              |
| 72              | 予約日時が新しい日付に更新され「予約を更新しました」が表示される                 |
| 48              | 予約日時が新しい日付に更新され「予約を更新しました」が表示される                 |
| 47              | 「変更期限を過ぎています。電話でお問い合わせください」が表示され予約は変更されない |
| 0               | 「変更期限を過ぎています。電話でお問い合わせください」が表示され予約は変更されない |

# SubTask候補
- [ ] フロントエンド: 予約変更画面のUI実装
- [ ] バックエンド: 予約変更API（PUT /reservations/{id}）
- [ ] バックエンド: 変更期限チェックロジック
- [ ] テスト: E2Eテスト（正常系・異常系）
```

### 悪い例 ❌

```markdown
# Title
予約変更機能を実装する

# 受け入れ条件
予約を変更できること
```

**問題点:**
- Title: 実装形式（「〜を実装する」）→ ユーザーストーリー形式ではない
- 元Requirement: リンクなし（トレーサビリティ欠如）
- 受け入れ条件: Gherkin形式ではない、曖昧

### 設計仕様混入の例 ❌（フォーマットはあるが内容がNG）

```markdown
# 受け入れ条件

## シナリオ1: 正常な日時変更
Given: ユーザーが予約詳細画面を表示している
When: ユーザーが新しい日付を選択し「更新」ボタンを押す
Then:
  - PUT /reservations/{id} APIが呼ばれ、DBのreservationsテーブルが更新される
  - フロントエンドが更新レスポンスを受け取り画面を再描画する
```

**問題点:**
- Then節: `PUT /reservations/{id}` → 設計仕様（SubTaskに記載すべき）
- Then節: `DBのreservationsテーブルが更新される` → インフラ詳細、ユーザーが観察できない
- Then節: `フロントエンドが〜再描画する` → 内部処理の記述

**修正後 ✅:**
```markdown
Then:
  - 予約日時が指定した日付に更新される
  - 「予約を更新しました」メッセージが表示される
  - 確認メールがユーザーに送信される
```

## 注意事項

- このAgentは**フォーマット準拠**と**Gherkin形式の品質**を主眼としています
- **Specification by Example の運用方針**: 受け入れ基準の本質は Gherkin 形式で書いていることではなく、**具体値を書いていること**。Gojko Adzic の10年フォローアップ調査（n=514, 2020）では、具体例を受け入れ基準として運用するチームと品質の間に強い相関が確認されている。曖昧な変数名や抽象表現のまま Story を Refinement 通過させない。
- **Gherkin内の設計仕様混入はNG**: API名・DBテーブル・エンドポイントはSubTaskに記載し、ACにはユーザーが観察できる振る舞いのみを記述すること
- 仕様の妥当性（本当にこの仕様で良いか等）は判定しません
- **受け入れ条件のGherkin形式は必須**です（これがないと検証できない）
- 曖昧表現（「正しく」「適切に」等）は**NG**です
- 異常系シナリオは**強く推奨**です（品質向上のため）
- Title形式が「願望形式」「解決意図形式」の場合、Issue Type変更を提案します
- Title形式が「実装形式」の場合、SubTask化を提案します
- **Mock Type は Story に必須**: Vision / Sales / Build / N-A のいずれかを設定する。N-A は画面開発を含まない Story（バックエンドのみ等）に使用する
- **Workflow StateはStory/Task/SubTaskのみのプロパティ**: Issue（Tech/Needs/Bug/Request）には存在しない
- **Planned Release Versionは In Sprint 時点で必須**: 未設定のままスプリントに投入されている場合は指摘する
- **Released Versionは Done 後に設定**: Done になってリリースが完了したら必ず設定すること
