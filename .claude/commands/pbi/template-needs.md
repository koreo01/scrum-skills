# PBI Template Needs

check-needs.md のチェックを通過しやすい Needs チケットの雛形を出力します。

## コマンド形式

```
/pbi:template-needs [--title "タイトル"]
```

| 引数 | 説明 |
|-----|------|
| `--title "タイトル"` | タイトルをあらかじめ埋めた状態で出力 |
| （省略） | 全フィールドが空欄の雛形を出力 |

---

## 使い方

> **議事録由来で作成する場合**: 先に `/pbi:invoke-story-ticket-helper` を実行してチケット候補を抽出してください。

1. このコマンドを実行すると、下記テンプレートを出力します
2. `[...]` で囲まれた部分を実際の内容に置き換えてください
3. 記載後に `/pbi:check-needs` で品質確認してください

---

## 空・雨・傘における位置づけ

Needs は「空・雨・傘」フレームワークの **空（事実）＋雨（解釈）** の層です。

```text
空（事実）  ←── Needs「事実（空）」セクション：観察・発言・記録などの生データ
     ↓ 事実をもとに意味を読み取る
雨（解釈）  ←── Needs「解釈（雨）」セクション：事実から何を読み取るかの推論
     ↓ 解釈をもとに対応策を定義する
傘（対応）  ←── Requirement → Story へ続く
```

**なぜ分けるか**: 事実に解釈を混ぜると、後から別の解釈が立てにくくなります。
空（事実）は誰が見ても同じ「起きたこと」、雨（解釈）は「それをどう読むか」として、
必ず別セクションに記録してください。

## 出力テンプレート

以下のテンプレートをそのまま出力する：

```markdown
# [Needsタイトル]
<!-- Title形式: 「〇〇したい」（顧客・ユーザーの要望形式） -->
<!-- NG例: 「〇〇機能を実装する」（実装形式） / 「〇〇が動かない」（Bug形式） -->
[ユーザー]が[何かを]したい

## 事実（空）
<!-- 空 = 誰が見ても同じ「起きたこと」。推測・解釈を混ぜない -->
<!-- 必須: 4種類のうち1つ以上を選んで記載 -->
<!-- ① 記録: [いつ]、[システム/ツール名] に [こう記録されている]。 -->
<!-- ② 発言: [いつ・どこで]、[誰] が [こう言った/書いた]。 -->
<!-- ③ 伝聞: [誰] から、[別の誰] が [こう言っていた] と聞いた。 -->
<!-- ④ 観察: [いつ・どこで]、私は [こうなっているの] を見た/聞いた。 -->

[YYYY/MM/DD（または具体的な時期）]、[誰/システム] が/に [具体的な内容]。

## 解釈（雨）
<!-- 雨 = 空（事実）から何を読み取るかの推論。必ず事実セクションと分離する -->
<!-- 必須: 事実から何を読み取るかを記載 -->
[上記の事実] から、[こういう意味だ] と私は読んでいる。
なぜなら [この事実] と [別の知識・事実・経験] を結びつけているからだ。
（ただし [別の結びつけ方] もありうる。）
<!-- 注: 「ただし〜もありうる」は省略すると check-needs.md で⚠️ -->
```

## GitHub ラベル設定ガイド

| プロパティ | 値 | 設定タイミング |
|-----------|-----|-------------|
| Type | Needs | 作成時 |
| Status | Triage | 起票時（調査・判断待ち） |
| Owner | Business | 起票〜Refiningまで（必須） |
| Status | Story Defined 以降 | ProductへOwner移行のタイミング |

### Owner × Status の整合ルール

| Status | Owner |
|--------|-------|
| Triage / Refining | Business |
| Story Defined 以降 | Product |

## check-needs.md チェック項目との対応

| チェック項目 | テンプレートの対応箇所 |
|------------|----------------------|
| 0-1 Status有効値 | プロパティ設定ガイド参照 |
| 0-2 Owner設定 | プロパティ設定ガイド参照 |
| 0-3 Owner×Status整合 | Owner × Status の整合ルール参照 |
| 1 事実（空）セクション存在 | `## 事実（空）` セクション |
| 2 解釈（雨）セクション存在 | `## 解釈（雨）` セクション |
| 3 セクション分離 | 空（事実）と雨（解釈）を別セクションに記載 |
| 4 プレースホルダー残存なし | `[...]` をすべて埋める |
| 5 事実の種類明示 | コメントの①〜④から選択 |
| 6 時間情報の具体性 | 「YYYY/MM/DD」または具体的な時期 |
| 7 人物情報の具体性 | 氏名または役職で記載 |
| 8 事実→解釈の参照 | 解釈の冒頭で事実を引用 |
| 9 別解釈の言及 | 「ただし〜もありうる」の一文 |

## よくある記載ミス

| ミスのパターン | 正しい書き方 |
|-------------|------------|
| 事実（空）に解釈が混入: 「〇〇さんが不満を感じているようだ」 | 「〇〇さんが『使いにくい』と言った」（観察・発言のみ）。推測は解釈（雨）セクションへ |
| 解釈（雨）に事実が混入: 「〇〇さんが言ったから〜すべきだ」 | 事実（空）セクションを先に書き、解釈は「〜と私は読んでいる」の形で分離 |
| 事実: 「先週、〇〇さんが〜と言った」 | 「2026/03/25（火）、〇〇さんが〜と言った」（具体的な日付） |
| 事実: 「顧客から要望があった」 | 誰が・いつ・どこで言ったかを明記 |
| 解釈なし | 必ず「〜と私は読んでいる。なぜなら〜」を追記 |
| 別解釈の記載なし | 「ただし〜もありうる」で代替解釈を示す（チェックで⚠️） |
| 事実と解釈が混在 | 空（事実）セクションと雨（解釈）セクションを明確に分離 |
