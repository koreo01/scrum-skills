# PBI Check Backbone Agent

Backboneチケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-backbone [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/backbone-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のBackboneチケットをチェック
/pbi:check-backbone #123

# チェック結果をファイルに保存
/pbi:check-backbone #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-backbone #123 --gh-comment

# 両方（ファイル保存 + GitHub Issueコメント）
/pbi:check-backbone #123 --save --gh-comment

# ローカルファイルをチェックして保存
/pbi:check-backbone @docs/issues/user-onboarding-backbone.md --save

# 対話モード
/pbi:check-backbone
```

## Backbone の位置づけ

```
Backbone（テーマ・大きな目標）  ← このAgentが対象
  └─ Narrative Flow（ユーザーシナリオの流れ）
       └─ Story（具体的な機能仕様・受け入れ条件）
            └─ SubTask（実装作業単位）
```

**Backbone** = 「プロダクトが実現したい大きなテーマ・エピック・価値領域」

Backbone は階層の最上位に位置し、親チケットを持たない。配下に Narrative Flow（またはシンプルな場合は直接 Story）を持つ。「何を・なぜ実現するか」という方向性・目標を定義し、Narrative Flow が「どのようにユーザーが動くか」のシナリオを定義する。

### Title/Summary のパターン

| パターン | 例 |
|---------|-----|
| 〇〇の改善 | 「ユーザーオンボーディング体験の改善」 |
| 〇〇の強化 | 「検索機能の精度強化」 |
| 〇〇の刷新 | 「管理者ダッシュボードUIの刷新」 |
| 〇〇の実現 | 「マルチテナント対応の実現」 |

### Backbone / Narrative Flow / Story との違い

| 観点 | **Backbone** | Narrative Flow | Story |
|------|-------------|----------------|-------|
| 抽象度 | **最も高い（テーマ・エピック）** | 中間（ユーザーシナリオ） | 低い（具体的な機能仕様） |
| 主語 | **製品・サービス全体、ビジネス目標** | 特定のユーザー・ペルソナ | ユーザー（受け入れ条件） |
| 記述内容 | **達成したい大目標・価値** | ユーザーの行動シナリオの流れ | Given/When/Then（Gherkin） |
| 親チケット | **なし（最上位）** | 親Backbone | 親Narrative Flow / Backbone |
| 子チケット | **Narrative Flow（またはStory）** | Story | SubTask |

## Statusライフサイクル・Owner

### Statusライフサイクル

Backbone は「ビジネス部門向け」の最上位計画アーティファクトであり、スプリント管理プロパティ（Workflow State等）は持たない。Statusは3段階のみ有効。

| Status | 意味 | Ownerの目安 |
|--------|------|------------|
| Refining | テーマ・目標を精査中 | Business |
| Story Defined | 配下のNarrative Flow（またはStory）が定義済み | Product |
| Done | 配下Narrative Flow/Storyがすべて完了 | Product |

### Owner

| タイミング | Owner |
|-----------|-------|
| Refining | Business |
| Story Defined 以降 | Product |

## チェック対象テンプレート

### Backboneの必須要素

| フィールド | 必須事項 | 例 |
|-----------|---------|-----|
| **Title** | テーマ/目標形式（「〇〇の改善」「〇〇の強化」等） | 「ユーザーオンボーディング体験の改善」 |
| **概要** | このBackboneが実現したい大目標・価値の要約 | 新規ユーザーが最初の7日間で... |
| **対象ユーザー/顧客セグメント** | 恩恵を受けるユーザーの属性・顧客セグメント | 新規登録ユーザー全般 |
| **ゴール/理想状態** | このBackboneが達成されたときの理想状態・指標 | 初回ログイン完了率が90%以上 |
| **配下Narrative Flow** | 子Narrative FlowへのリンクまたはStoryリンク（Story Defined以降は必須） | #xxxx「新規ユーザーが初回ログインするフロー」 |

### Backboneテンプレート

```
【概要】
[このBackboneが実現したい大目標・価値の要約]

【対象ユーザー/顧客セグメント】
[このBackboneの恩恵を受けるユーザー・顧客セグメントの属性]

【ゴール/理想状態】
[このBackboneが達成されたときに実現している状態・指標]
例: 〇〇率が△△%以上、〇〇件数が△△%削減

【配下Narrative Flow】（Status=Story Defined以降は必須）
- [ ] #xxxx: [Narrative Flow1のタイトル（「〇〇が△△するフロー」形式）]
- [ ] #xxxx: [Narrative Flow2のタイトル]
```

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Refining / Story Defined / Done のいずれか |
| 0-2 | Ownerの設定 | Business または Product が設定されている |
| 0-3 | Owner×Statusの整合 | Refining は Business、Story Defined 以降は Product |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | Title形式 | テーマ/目標形式（「〇〇の改善」「〇〇の強化」「〇〇の実現」等） |
| 2 | 概要/目的の存在 | このBackboneが実現したい大目標・価値の説明がある |
| 3 | 対象ユーザー/顧客セグメントの記述 | 恩恵を受けるユーザー属性または顧客セグメントが記述されている |

### Phase 2: フォーマット準拠チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | 配下Narrative Flow/Storyリンク | Status=Story Defined/Done の場合、子Narrative FlowまたはStoryへのリンクが1件以上ある |
| 5 | ゴール/理想状態の記述 | このBackboneが達成されたときの状態・価値が記述されている |
| 6 | スコープの示唆 | Backboneが何を対象とし何を含まないかが示唆されている |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 7 | ビジネス/ユーザー価値視点 | ビジネス価値またはユーザー価値の観点で記述されている（実装詳細なし） |
| 8 | Narrative Flow分解可能性 | このBackboneからNarrative Flowに分解できる粒度になっている |
| 9 | タイトル・概要・ゴールの一貫性 | タイトルが示すテーマと概要・ゴールが整合している |

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ テーマ/目標形式 | `〜の改善`, `〜の強化`, `〜の刷新`, `〜の実現`, `〜の向上`, `〜の最適化` |
| ❌ フロー/シナリオ形式 | `〜するフロー`, `〜から〜まで`, `〜のシナリオ`（→ Narrative Flowの可能性） |
| ❌ 機能形式 | `〇〇は△△できる`（→ Storyの可能性） |
| ❌ 作業形式 | `〜を実装する`, `〜を改修する`（→ Task/SubTaskの可能性） |

### 配下Narrative Flow/Storyリンクの判定

| Status | 判定 | ルール |
|--------|------|--------|
| Refining | ⚠️ 推奨 | なくても問題ないが追加を推奨 |
| Story Defined | ❌ 必須 | 1件以上のNarrative FlowまたはStoryリンクが必要 |
| Done | ❌ 必須 | 1件以上のNarrative FlowまたはStoryリンクが必要 |

### ゴール/理想状態の具体性判定

| 判定 | パターン例 |
|------|----------|
| ✅ 具体的 | 「初回ログイン完了率90%以上」「支援問い合わせ件数30%削減」「〇〇がXXできる状態」 |
| ⚠️ 曖昧 | 「使いやすくする」「改善する」「強化する」（定量・定性の達成状態なし） |
| ❌ なし | ゴール・理想状態の記載がない |

### ビジネス/ユーザー価値視点の判定（概要・ゴール内）

| 判定 | パターン |
|------|---------|
| ✅ 価値視点 | ユーザー・顧客のベネフィット、ビジネス成果として記述されている |
| ❌ 実装詳細混入 | `APIを設計する`, `DBスキーマを変更する`, `マイクロサービス化する` |
| ❌ 作業視点 | 「〜を実装する」「〜を改修する」のみで価値・目標が不明 |

## 良い例・悪い例

### 良い例 ✅

```markdown
# Title
ユーザーオンボーディング体験の改善

# 概要
サービスに新規登録したユーザーが、最初の7日間でコア機能を自力で使いこなせる状態に到達できるよう、
オンボーディングフロー全体を見直す。

# 対象ユーザー/顧客セグメント
新規登録ユーザー（契約後7日以内）、特にITリテラシーが平均的な現場担当者

# ゴール/理想状態
- 初回ログイン完了率: 90%以上
- チュートリアル完了率: 70%以上
- 登録後7日以内のサポート問い合わせ件数: 30%削減

# 配下Narrative Flow
- [ ] #1210: 「新規ユーザーが招待メールを受け取り初回登録を完了するフロー」
- [ ] #1211: 「新規ユーザーが初回ログインからダッシュボード確認まで行うフロー」
- [ ] #1212: 「ユーザーがチュートリアルを完了して主要機能を習得するフロー」
```

### 悪い例 ❌

```markdown
# Title
ログイン機能の改善

# 概要
ログイン周りの実装を改修してUXを良くする。
APIのレスポンスを速くして認証フローを最適化する。

# 配下Narrative Flow
（なし）
```

**問題点:**
- Title: 「ログイン機能の改善」はBackboneとしては粒度が小さすぎる（Narrative Flowレベルの可能性）
- 概要: 実装詳細（API・認証フロー最適化）になっており、ユーザー価値・ビジネス目標が見えない
- ゴール/理想状態: なし
- 対象ユーザー/顧客セグメント: なし
- 配下Narrative Flowリンク: なし

## 注意事項

- このAgentは**フォーマット準拠**を主眼としています
- テーマの妥当性（このBackboneを実施するべきかどうか等）は判定しません
- **配下Narrative Flow/StoryリンクはStory Defined以降で必須**: Refining 時点では推奨、Story Defined に移行する前に必ず追加すること
- **BackboneはNarrative Flowと異なり親チケットを持たない**: 親チケットリンクのチェックは不要
- **Workflow StateはBackboneには存在しない**: Story/Task/SubTaskのみのプロパティ
- **Status は3段階のみ有効**: Triage ではなく Backbone / Narrative Flow 固有の3段階（Refining / Story Defined / Done）
- Title形式がフロー/シナリオ形式（「〜するフロー」等）の場合、Narrative Flow化を提案します
- Title形式が機能形式（「〇〇は△△できる」）の場合、Story化を提案します
- ゴール/理想状態は定量指標が望ましいが、定性的な理想状態でも✅とする（⚠️は「なし」の場合のみ）
