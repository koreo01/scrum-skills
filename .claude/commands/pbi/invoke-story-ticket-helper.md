# PBI Invoke Story Ticket Helper

議事録などの会話ログから Needs / Requirement / Story / Task の **IssueType チケット候補** を抽出し、
既存の `template-*` フォーマットに**仮草稿**して提示するヘルパーです。

このスキルは、**チケット起票担当者自身が「情報の属性（空・雨・傘）」と「AI が読みやすいフォーマット」を確認・認識できる状態**
を作ることを最大の目的とします。自動化ツールではなく**対話的ヘルパー**として動作します。

---

## コマンド形式

```
/pbi:invoke-story-ticket-helper [source] [mode]
```

### ソース指定方法（Phase 1）

| 形式 | 説明 | 例 |
|------|------|-----|
| `gemini-memo:URL` | Google Drive 上の Gemini メモ URL | `gemini-memo:https://docs.google.com/document/d/...` |
| `gemini-memo:@file` | ローカルの議事録 MD ファイル | `gemini-memo:@docs/meetings/2026-05-21.md` |
| （省略） | 対話モード（議事録テキストを貼り付け） | - |

### ソース指定方法（Phase 2 以降・将来拡張）

| 形式 | 説明 | 状態 |
|------|------|-----|
| `notion:URL` | Notion ページ（まとめ記事） | 🔧 未実装 |
| `slack:channel/thread-ts` | Slack スレッド | 🔧 未実装 |

入力ソースは **ソースアダプター層** で抽象化され、Phase 1 では `gemini-memo:` のみ実装する。
Phase 2 で他ソースを追加しても、コア（分類・仮草稿）を再利用できる構造とする。

### モード

| モード | フラグ | 用途 |
|--------|-------|------|
| **A: Explain モード** | `--explain` (デフォルト) | 発言ごとに属性タグを付け、空・雨・傘の構造を可視化する |
| **B: Draft モード** | `--draft` | 選択した候補を `template-*` 形式に仮草稿してドラフト出力 |
| **C: Check Ready モード** | `--check-ready` | Draft 完了後、対応する `/pbi:check-*` の実行を提案する |

### 使用例

```bash
# Explain モード（議事録の属性を学習）
/pbi:invoke-story-ticket-helper gemini-memo:https://docs.google.com/document/d/...

# Draft モード（候補をテンプレ仮草稿）
/pbi:invoke-story-ticket-helper gemini-memo:@docs/meetings/2026-05-21.md --draft

# Check Ready モード（チェックチェーンへ誘導）
/pbi:invoke-story-ticket-helper gemini-memo:@docs/meetings/2026-05-21.md --check-ready
```

## 空・雨・傘における位置づけ

このヘルパーは、**会話 → 空・雨・傘・仕様への分解**を担当します。

```text
会話（議事録）        ← このスキルの入力
     ↓ 発言の属性タグ付け
空（事実）            ← Needs「事実（空）」セクションに仮草稿
雨（解釈）            ← Needs「解釈（雨）」セクションに仮草稿
傘（対応の方向性）    ← Requirement「解決すること」に仮草稿
傘（仕様展開）        ← Story「受け入れ条件」の Gherkin 骨格を仮置き
作業の定義            ← Task の「完了条件」骨格を仮置き
```

**このスキルは起票を確定させない**。
必ず Draft までで止め、担当者自身が `template-*` を参照しながら整形し、
`check-*` で品質確認する。チェーンに乗せる。

---

## ワークフロー全体

```
議事録（Gemini メモ）
    ↓
/pbi:invoke-story-ticket-helper（このスキル）
    ├─ Step 1: 議事録の取り込み・正規化
    ├─ Step 2: 「次のステップ」と「文字起こし」の構造抽出
    ├─ Step 3: 発言ごとの空・雨・傘・対応の属性タグ付け
    ├─ Step 4: IssueType 候補の生成（複数候補を必ず提示）
    ├─ Step 5: 候補の粒度判定（チケット化 / 個人 ToDo / 保留）
    └─ Step 6: モードに応じた出力
         ├─ Explain: 属性タグ付きの議事録ビュー
         ├─ Draft: template-* 形式の仮草稿 MD
         └─ Check Ready: 次に走らせる /pbi:check-* の提案
    ↓ （担当者が選択・編集）
/pbi:template-needs / template-requirement / template-story / template-task
    ↓
チケット管理ツールへ起票
    ↓
/pbi:check-needs / check-requirement / check-story / check-task
```

---

## Step 1: 議事録の取り込み・正規化

ソースアダプターで議事録テキストを取得し、以下のセクションに分解する。

| Gemini メモのセクション | 用途 |
|------------------------|------|
| `### 概要` | チケット候補の Title ヒント |
| `### 次のステップ` | **最優先で IssueType 候補に変換** |
| `### 詳細`（タイムスタンプリンク付き） | 空（事実）の出処として利用 |
| `## 文字起こし` | 発言レベルの属性タグ付けの素材 |

他ソース（Notion / Slack）は、それぞれのアダプターでこの正規形に変換する。

---

## Step 2: 「次のステップ」と「文字起こし」の構造抽出

### 「次のステップ」の解析

Gemini メモの「次のステップ」は、すでに「担当者 + アクション」の形式で書かれているため、
**IssueType 候補の最有力ソース**として扱う。

例:

```
[Aさん] 検証用スクリプト作成: データを検証可能にするためにスクリプト化のタスクを起票する
```

→ **Task 候補の第一候補**（本文に「タスクを起票する」と明示されている）

```
[Aさん] マネージャーへの連絡: 機能改善案に関する戦略を整理してマネージャーに Slack で送付、POをCCに入れる。
```

→ Step 5 で**個人 ToDo に分類される可能性が高い**として保留候補に振り分ける。

### 「文字起こし」の解析

タイムスタンプ単位（例: `### 00:09:27`）で発言ブロックを分割し、発言者ごとに取り出す。

---

## Step 3: 発言ごとの空・雨・傘・対応の属性タグ付け

各発言に対して以下のタグ候補を付与する（複数タグ可）。

| タグ | 検出パターン | 例 |
|-----|------------|-----|
| **【空（事実）】** | 「〜と言っていた」「〜の数字が出た」「〜という観察・報告があった」 | 「レビューで「想定と違う挙動になる」という観察」 |
| **【雨（解釈）】** | 「〜と思う」「〜だろう」「〜の方が良い」 | 「案Aの方が案Bより低コスト」 |
| **【傘（対応方向）】** | 「〜した方がいい」「〜が必要」「〜すべき」「〜してほしい」 | 「Human-in-the-loop のストーリーはほしいと思っている」 |
| **【判断/結論】** | 「結論として」「方針として」「〜でいきましょう」 | 「この方針でいきましょう、それが一番シンプル」 |
| **【未決/保留】** | 「どっちかな」「迷っている」「じゃあ待ってみます」 | 「どっちかはまだ確認待ち。マネージャーと話してみます」 |
| **【提案】** | 「やってみたい」「どうでしょう」 | 「この検証はやってみたい」 |
| **【個人 ToDo】** | 「連絡する」「送る」「共有する」「準備する」 | 「夕方までに資料を整理して送る」 |

### 発言者属性の保持

各発言には必ず **発言者** を残す:

- 【発言者:PO】 → PO/マネージャー、戦略の指示・提案が多い
- 【発言者:担当者】 → 起票担当者、技術検証・実装観点
- 【発言者:他】 → 議事録に登場する第三者（上長・関係者・クライアント等）

これにより、後で Needs の Owner や Story の責任者を割り振りやすくなる。

### タイムスタンプリンクの保持

すべての発言には **元のタイムスタンプリンク**(`00:09:27` 等)を保持し、Draft モードで出力する空（事実）セクションに
出処として埋め込む。

---

## Step 4: IssueType 候補の生成

タグ付けされた発言を組み合わせて、IssueType 候補を生成する。

### 生成ルール

| IssueType | 生成条件 |
|-----------|---------|
| **Backbone 候補** | テーマ・大目標レベルの議論で、対象ユーザー/顧客セグメントが明示されている（エピック・ロードマップ文脈） |
| **Narrative Flow 候補** | ユーザーシナリオの流れ（誰がどこからどこまで）を議論している（ユーザーストーリーマッピング文脈） |
| **Needs 候補** | 【空（事実）】+【雨（解釈）】が同一か近傍のブロックで揃っている |
| **Requirement 候補** | 【傘（対応方向）】が【判断/結論】と共に出ている、かつ傘になれる雨（解釈）を辿れる |
| **Story 候補** | 【傘（対応方向）】がユーザー視点の振る舞いとして具体化されている |
| **Task 候補** | 「次のステップ」に「起票する」「タスク化」と明示、または明確な作業単位 |

### IssueType の階層イメージ

```text
Backbone（テーマ・エピック）
  └─ Narrative Flow（ユーザーシナリオの流れ）
       └─ Story（ユーザー視点の振る舞い）
            └─ Task（作業単位）
```

Backbone/Narrative Flow が候補になるケースは、1 回の会議で複数 Story にまたがる戦略的な議論が行われた場合に限る。
多くの場合は Needs〜Task の範囲での起票を推奨する。

### 必ず複数候補を提示する

1つの会議で複数トピックが並走するケースでは:

- 機能改善案A（優先度高）
- 機能改善案B（優先度低）
- データ検証スクリプト作成
- 新方式の技術検証
- 切り替え可能な設計の検討

これらをすべて候補として一覧化し、担当者が「どれをチケット化するか」を選ぶ。
**1つだけ抽出して終わらせない**こと（見落としの原因）。

---

## Step 5: 候補の粒度判定（チケット化 / 個人 ToDo / 保留）

各候補について、以下の3分類に振り分ける。

| 分類 | 判定基準 | 例 |
|------|---------|-----|
| **チケット化候補** | スプリント工数として扱うべき作業 | データ検証スクリプトの作成 |
| **個人 ToDo** | チケット起票不要の連絡・準備・調査依頼 | マネージャーに Slack で戦略を送付 |
| **判断保留** | 議事録時点で未決のもの | 機能改善案の優先順位（マネージャー判断待ち） |

**判定はあくまで提案**であり、担当者が対話モードで上書きできる。

### 個人 ToDo の特徴

- 「連絡する」「送る」「共有する」「準備する」
- 対象が個人（マネージャーに / POに）
- 完了条件が発話（送ったら終わり）

これらは PBI 起票しない。

### 判断保留の特徴

- 議事録前で「どっちかな」「マネージャーと話してみます」などが、合意形成されていない
- → Needs 候補として残しつつ、Owner: Business / Status: Triage の前提で扱う

### モード B: Draft モード

選択された候補（または上位候補）を `template-*` 形式に仮草稿して出力する。
出力は **既存の template-* と同一フォーマット**で、check-* を通せる構造を目指す。

```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 元Issue
【元Issue】[要起票] Needs「対象選択ができない問題」
  ⚠️ 元 Needs が未起票です。先に Needs を起票してください。

## 解決すること
利用者がレビューで感じる、
「想定と違う挙動になる」問題に対して、
対象選択（チェックボックス等）を提供することで解決する。

## 達成条件
Given: ユーザーがレビュー画面を表示している
When: 改善対象として特定の項目だけを選択して「自動改善」を実行する
Then: 選択した項目のみが改善され、未選択の項目は変更されない

- 精度向上ニーズ
- ユーザーのストレス軽減ニーズ
```

### モード C: Check Ready モード

Draft 完了後、対応する `/pbi:check-*` の実行を**自動実行せず提案**する。

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📍 起票チェーンの提案
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Draft 候補は以下の順で起票可能です:

Step 1: Needs を先に起票
  → /pbi:template-needs --title "対象外まで変更される問題"
  → 編集後 /pbi:check-needs @docs/issues/needs-XXX.md

Step 2: Requirement を起票
  → /pbi:template-requirement --title "機能改善案Aを優先実装できるようにする"
  → 編集後 /pbi:check-requirement @docs/issues/req-XXX.md

Step 3: Story を起票
  → /pbi:template-story --title "ユーザーは改善対象を選択して自動改善を実行できる"
  → 編集後 /pbi:check-story @docs/issues/story-XXX.md

Step 4 (任意): 縦スライス分割
  → /pbi:slice-story notion:URL

実行を選択してください:
  [1] Step 1 から順に進む
  [2] 特定の Step だけ実行する（番号で指定）
  [3] 終了（ドラフトのみで完了）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## ガードレール（議事録抽出特有）

既存スキルのガードレールに加え、議事録抽出固有のリスクに対処する。

| # | ガードレール | 議事録の例 |
|---|------------|-----------|
| G1 | **複数候補を必ず提示** | 1 回の会議に 5 トピック並走 → 1 つだけ抽出して終わらせない |
| G2 | **発言者属性を保持** | PO発言 vs 担当者発言 vs 上長代弁を区別 |
| G3 | **仮説と事実の分離** | 議事録の発言は事実（空）、ただし Skill が読み取った内容は雨、Draft 時に混ぜない |
| G4 | **タイムスタンプリンクの保持** | 空（事実）セクションの出処として `00:09:27` 等を必ず残す |
| G5 | **未決事項を確定として書かない** | 「どっち側未確定」は Draft で「決定」と書かない |
| G6 | **顧客名・個人名の取り扱い** | レビュー・上長・お客様代弁などは、起票時の扱いは確認が必要 |
| G7 | **個人 ToDo を起票候補に混ぜない** | 「Slack で送る」「夕方までに資料を整理」等は PBI 化しない |
| G8 | **元 Issue 未起票の警告** | Requirement / Story を作る前に元 Needs があるか確認 |
| G9 | **自動確定起票の禁止** | 必ず Draft までで止め、担当者の編集・check を経由する |
| G10 | **会議前合意レベルの明示** | 「PO・担当者合意済み」「上長未確認」「全社合意」を区別 |
| G11 | **メタ会議判定** | チケット化候補が少ない会議（次スプリント準備・段取り会議）では無理に候補を絞り出さず「この会議はチケット化対象が少ない」と素直に伝える |
| G12 | **起票意図シグナル検出** | 「PBI にしたい」「チケットにしたい」「次のスプリントで」等の発言を最優先候補として一覧の先頭に表示する |

### G12 起票意図シグナルの検出パターン

以下の発言パターンを含む候補は、Explain モードの一覧で ★ 最優先マークを付けて先頭に表示する。

| パターン種別 | 検出キーワード例 |
| --- | --- |
| 明示的起票意図 | 「PBI にしたい」「チケットにしたい」「起票したい」「バックログに入れたい」 |

### G11 メタ会議判定の動作

チケット化候補が 1 件以下の場合、Explain モードの冒頭に以下を表示する:

```text
⚠️ この会議はチケット化候補が少ない会議（メタ会議）と判定しました。
   内容: 次スプリント準備・段取り確認などの調整が主目的と見られます。
   無理にチケット候補を絞り出さず、実際に見つかった候補のみを提示します。
```

候補 0 件の場合は Draft モードへの誘導も省略する。

## 注意事項

- このスキルは **自動起票ツールではない**。必ず Draft までで止める。
- 議事録の発言は **AI 文字起こし** のため、誤字・誤認識を含む。文脈で補正するが、Draft 時に「※文字起こし要確認」マークを残す。
- **空・雨・傘の分類精度** はスキルが完璧にできることを保証しない。担当者自身が Explain モードで確認すること。
- 「次のステップ」セクションを最優先で見るが、文字起こし前に隠れている重要トピックを見落とさないように。
- **個人 ToDo を Task と混同しない** ことが最重要ガードレールとする。
