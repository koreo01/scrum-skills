# PBI Check Needs Agent

Needsチケットが「事実（空）」と「解釈（雨）」のテンプレートフォーマットに沿って記載されているかをチェックするガードレールです。

## 空・雨・傘における位置づけ

```text
空（事実）  ←── Needs「事実（空）」：観察・発言・記録などの生データ
     ↓ 事実をもとに意味を読み取る
雨（解釈）  ←── Needs「解釈（雨）」：事実から何を読み取るかの推論
     ↓ 解釈をもとに対応策を定義する
傘（対応）  ←── Requirement → Story へ続く
```

Needs の役割は **空（事実）と雨（解釈）を切り離して記録する** ことです。
事実に解釈が混入すると、後から別の解釈が立てにくくなります。

## コマンド形式

```
/pbi:check-needs [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/needs-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のNeedsチケットをチェック（画面表示のみ）
/pbi:check-needs #123

# チェック結果をファイルに保存
/pbi:check-needs #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-needs #123 --gh-comment

# 両方（ファイル保存 + GitHub Issueコメント）
/pbi:check-needs #123 --save --gh-comment

# ローカルファイルをチェックして保存
/pbi:check-needs @docs/issues/customer-dashboard.md --save

# 対話モード
/pbi:check-needs
```

## 出力ファイル

### `--save` オプション使用時

出力先: `analysis/format-check/YYYY-MM-DD_<ticket-id>.md`

```markdown
# フォーマットチェック結果

- **チケット**: #676「ユーザーとして、プロンプトの更新状況を確認したい」
- **チェック日時**: 2026-04-01 12:24
- **スコア**: 75/100（⚠️ 要改善）

## 指摘事項

### ⚠️ プレースホルダー残存
- 箇所: ページプロパティ「背景」
- 現在の記載: `なぜなら、XXXXでYYYYだからだ。`
- 対応: XXXX / YYYY を実際の内容で埋めてください

### ⚠️ 時間情報が曖昧
- 箇所: 事実セクション
- 現在の記載: `先週のMTGで...`
- 対応: 具体的な日付（例: 2026/03/25）に変更

## 次のアクション

1. [ ] 背景プロパティの XXXX / YYYY を実際の内容で埋める
2. [ ] 時間情報を具体的な日付に変更
3. [ ] 修正後に再度 `/pbi:check-needs` で確認
```

### `--gh-comment` オプション使用時

GitHub Issue のコメントに以下が追記されます：

```

スコア: 75/100（⚠️ 要改善）

⚠️ 時間情報が曖昧: 具体的な日付に変更してください

修正後に再度チェックをお願いします。
```

### Statusライフサイクル

| Status | 意味 | Ownerの目安 |
|--------|------|------------|
| Triage | 調査・判断待ち | Business |
| Refining | Refinement中 | Business |
| Story Defined | Story / Task 起票済み | Product |
| In Sprint | 対応作業中 | Product |
| Done | 完了 | Product |

### Owner

| タイミング | Owner |
|-----------|-------|
| 起票〜Refining | Business |
| Story Defined以降 | Product |

## チェック対象テンプレート

### 事実（空）テンプレート（4種類のいずれか）

空 = 誰が見ても同じ「起きたこと」。推測・解釈を混ぜないこと。

| 種類 | フォーマット | 必須要素 |
|------|------------|---------|
| **記録** | `[いつ]、[システム/ツール名] に [こう記録されている]。` | いつ、システム名、記録内容 |
| **直接の発言** | `[いつ・どこで]、[誰] が [こう言った/書いた]。` | いつ・どこで、誰、発言内容 |
| **伝聞** | `[誰] から、[別の誰] が [こう言っていた] と聞いた。` | 情報源、発言者、内容 |
| **観察** | `[いつ・どこで]、私は [こうなっているの] を見た/聞いた。` | いつ・どこで、観察内容 |

### 解釈（雨）テンプレート

雨 = 空（事実）から何を読み取るかの推論。必ず事実セクションと分離すること。

```text
[この事実] から、[こういう意味だ] と私は読んでいる。
なぜなら [この事実] と [別の知識・事実・経験] を結びつけているからだ。
（ただし [別の結びつけ方] もありうる。）
```

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Triage / Refining / Story Defined / In Sprint / Done のいずれか |
| 0-2 | Ownerの設定 | Business または Product が設定されている |
| 0-3 | Owner×Statusの整合 | Triage・Refining は Business、Story Defined 以降は Product |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | 事実（空）セクション存在 | 「事実（空）」「事実」または4種類のキーワードが含まれる |
| 2 | 解釈（雨）セクション存在 | 「解釈（雨）」「解釈」または「〜と私は読んでいる」が含まれる |
| 3 | 空・雨のセクション分離 | 事実（空）と解釈（雨）が明確に分かれている |

### Phase 2: フォーマット準拠チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | プレースホルダー残存 | `[いつ]` `[誰]` 等の未記入がない |
| 5 | 事実の種類明示 | 4種類のどれか判別可能 |
| 6 | 時間情報の具体性 | 「いつ」が日付・時期で記載されている |
| 7 | 人物情報の具体性 | 「誰」が具体名または役職で記載されている |

### Phase 3: 整合性チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 8 | 事実→解釈の参照 | 解釈が事実を参照している |
| 9 | 別解釈の言及 | 「ただし〜もありうる」が記載されている |

## パターン検出ルール

### 事実の種類を判定するキーワード

| 種類 | 検出パターン |
|------|------------|
| 記録 | `記録`, `ログ`, `データ`, `〜に記録`, `〜と表示` |
| 直接の発言 | `〜が言った`, `〜と言った`, `〜が書いた`, `聞いた話では` |
| 伝聞 | `〜から聞いた`, `〜によると`, `〜らしい`, `〜とのこと` |
| 観察 | `見た`, `観察した`, `確認した`, `私は〜を見た` |

### 解釈を判定するキーワード

| 検出パターン |
|------------|
| `〜と読んでいる`, `〜と解釈`, `〜と考える`, `〜だと思う` |
| `なぜなら`, `理由は`, `根拠は` |
| `ただし`, `一方で`, `別の見方` |

### 時間情報の具体性判定

| 判定 | パターン例 |
|------|----------|
| ✅ 具体的 | `2026/03/25`, `3月25日`, `先週火曜日`, `Q1定例MTGにて` |
| ⚠️ 曖昧 | `先週`, `最近`, `以前`, `この前` |
| ❌ なし | 時間に関する記載がない |

## 対話モード

`/pbi:check-needs` のみで実行した場合、対話形式で記載を促す：

```
📝 Needs フォーマット入力モード

以下のテンプレートに沿って記載してください：

---
【事実】（以下から1つ以上選んで記載）

□ 記録: [いつ]、[システム/ツール名] に [こう記録されている]。
□ 発言: [いつ・どこで]、[誰] が [こう言った/書いた]。
□ 伝聞: [誰] から、[別の誰] が [こう言っていた] と聞いた。
□ 観察: [いつ・どこで]、私は [こうなっているの] を見た/聞いた。

【解釈】
[この事実] から、[こういう意味だ] と私は読んでいる。
なぜなら [この事実] と [別の知識・事実・経験] を結びつけているからだ。
（ただし [別の結びつけ方] もありうる。）
---

入力してください:
> 
```

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 20点 | Status有効値・Owner設定・Owner×Status整合 |
| 構造チェック | 30点 | 事実・解釈セクションの存在 |
| フォーマット準拠 | 30点 | テンプレート形式への準拠度 |
| 整合性 | 20点 | 事実→解釈の論理的つながり |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | Refinementに進めてOK |
| 60-79 | ⚠️ 要改善 | 指摘箇所を修正してから進める |
| 0-59 | ❌ 要リライト | テンプレートに沿って書き直し |

---

## 空・雨の混在チェック

事実（空）セクション内に以下のパターンが含まれる場合、⚠️として指摘する。

| 検出パターン | 理由 | 改善例 |
| --- | --- | --- |
| `〜だろう`, `〜と思われる`, `おそらく〜` | 推測（雨）が混入 | 解釈（雨）セクションへ移動 |
| `〜のはずだ`, `〜に違いない` | 解釈（雨）が混入 | 解釈（雨）セクションへ移動 |
| `〜すべき`, `〜が必要だ` | 対策（傘）が混入 | Requirementへ |

---

## 注意事項

- このAgentは**フォーマット準拠**を主眼としています
- 内容の妥当性（解釈が正しいか等）は判定しません
- 「別解釈の言及」は推奨であり、必須ではありません（スコアには影響）
- 空（事実）への解釈混入は⚠️として指摘する（スコアに影響）
