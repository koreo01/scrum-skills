# PBI Check Tech Agent

Tech Issueチケットが「事実」と「解釈」のテンプレートフォーマットに沿って記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-tech [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/tech-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のTechチケットをチェック
/pbi:check-tech #123

# チェック結果をファイルに保存
/pbi:check-tech #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-tech #123 --gh-comment

# 両方（ファイル保存 + GitHub Issueコメント）
/pbi:check-tech #123 --save --gh-comment

# ローカルファイルをチェックして保存
/pbi:check-tech @docs/issues/deploy-time.md --save

# 対話モード
/pbi:check-tech
```

## Tech Issue の特徴

Tech Issueは**技術的課題・改善**を記録するIssueです。

### Title/Summary のパターン

TechIssueのタイトルは「現在の困った状態」を表す。「〜する」という行動で書くとTaskになる。

| カテゴリ | パターン | 例 |
|---------|---------|-----|
| 効率系 | `〜がやりづらい`、`〜に時間がかかる` | 「テストDBのセットアップがやりづらい」 |
| 属人系 | `〜しか作業できない`、`〜が属人化している` | 「本番DBのマイグレーションは田中さんしか作業できない」 |
| 欠如系 | `〜が存在しない`、`〜がない`、`〜が未整備` | 「改善指示を渡すインターフェースが存在しない」 |
| 品質系 | `〜が複雑すぎる`、`〜のカバレッジが低い`、`〜が理解しにくい` | 「ビジネスロジックが複雑でテストが書けない」 |
| 制約系 | `〜に対応できない`、`〜が制限される`、`〜でしか動かない` | 「特定環境でしか動作確認できない」 |

### Needs との違い

| 観点 | Needs | Tech |
|------|-------|------|
| 起点 | 顧客・ユーザーの要望 | 開発チーム内部の課題 |
| Title形式 | 「〇〇したい」（願望） | 「〇〇がやりづらい」（課題） |
| 背景の焦点 | なぜ顧客が必要としているか | なぜ技術的に問題なのか |

## Statusライフサイクル・Owner

### Statusライフサイクル

| Status | 意味 | Ownerの目安 |
|--------|------|------------|
| Triage | 調査・判断待ち | Business |
| Refining | Refinement中 | Business |
| Story Defined | Story / Task 起票済み | Product |
| In Sprint | 対応作業中 | Product |
| Done | 完了 | Product |

### Owner

| タイミング | Owner |
|-----------|-------|
| 起票〜Refining | Business |
| Story Defined以降 | Product |

## チェック対象テンプレート

### 事実テンプレート（4種類のいずれか）

| 種類 | フォーマット | Tech Issueでの例 |
|------|------------|-----------------|
| **記録** | `[いつ]、[システム/ツール名] に [こう記録されている]。` | 「3/25、CIログにビルド時間28分と記録されている。」 |
| **直接の発言** | `[いつ・どこで]、[誰] が [こう言った/書いた]。` | 「先週のレトロで、山田さんが『デプロイ待ちで作業が止まる』と言った。」 |
| **伝聞** | `[誰] から、[別の誰] が [こう言っていた] と聞いた。` | 「田中さんから、新人の佐藤さんが『手順書がなくて困った』と言っていたと聞いた。」 |
| **観察** | `[いつ・どこで]、私は [こうなっているの] を見た/聞いた。` | 「今週、私はCI待ちで3回手が止まったのを見た。」 |

### 解釈テンプレート

```
[この事実] から、[こういう意味だ] と私は読んでいる。
なぜなら [この事実] と [別の知識・事実・経験] を結びつけているからだ。
（ただし [別の結びつけ方] もありうる。）
```

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Triage / Refining / Story Defined / In Sprint / Done のいずれか |
| 0-2 | Ownerの設定 | Business または Product が設定されている |
| 0-3 | Owner×Statusの整合 | Triage・Refining は Business、Story Defined 以降は Product |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | 事実セクション存在 | 「事実」または4種類のキーワードが含まれる |
| 2 | 解釈セクション存在 | 「解釈」または「〜と私は読んでいる」が含まれる |
| 3 | セクション分離 | 事実と解釈が明確に分かれている |

### Phase 2: フォーマット準拠チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | Title形式 | 状態表現（効率系・属人系・欠如系・品質系・制約系のいずれか）。「〜する」で終わる作業動詞形式はNG |
| 5 | プレースホルダー残存 | `[いつ]` `[誰]` 等の未記入がない |
| 6 | 事実の種類明示 | 4種類のどれか判別可能 |
| 7 | 時間情報の具体性 | 「いつ」が日付・時期で記載されている |
| 8 | 影響範囲の記載 | 誰が・何が困っているか明記 |

### Phase 3: 整合性チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 9 | 事実→解釈の参照 | 解釈が事実を参照している |
| 10 | 別解釈の言及 | 「ただし〜もありうる」が記載されている |
| 11 | 定量データの有無 | 時間・回数・頻度などの数値がある（推奨） |

## 出力ファイル

### `--save` オプション使用時

出力先: `analysis/format-check/YYYY-MM-DD_<ticket-id>.md`

```markdown
# フォーマットチェック結果

- **チケット**: TECH-123「デプロイに時間がかかる」
- **チェック日時**: 2026-04-01 13:00
- **スコア**: 80/100（✅ Ready）

## 指摘事項

### ⚠️ 時間情報が曖昧
- 箇所: 事実セクション
- 現在の記載: `最近、デプロイ時間が長くなってきた。`
- 対応: 具体的な日付（例: 2026/03/20以降）に変更

### ⚠️ 定量データ不足
- 箇所: 事実セクション
- 対応: 時間（例: 28分→45分）や頻度（週3回）を追記

## 次のアクション

1. [ ] 時間情報を具体的な日付に変更
2. [ ] 定量データを追記
3. [ ] 修正後に再度 `/pbi:check-tech` で確認
```

### `--gh-comment` オプション使用時

GitHub Issue のコメントに以下が追記されます：

```
📋 フォーマットチェック結果（2026-04-01）
スコア: 80/100（✅ Ready）

【指摘事項】
⚠️ 時間情報が曖昧: 具体的な日付に変更してください
⚠️ 定量データ不足: 時間や頻度を追記してください

修正後に再度チェックをお願いします。
```

## パターン検出ルール

### Title形式の判定

| 判定 | パターン | 誘導先 |
| ---- | ------- | ------ |
| ✅ 効率系 | `〜がやりづらい`, `〜に時間がかかる`, `〜が遅い` | — |
| ✅ 属人系 | `〜しか作業できない`, `〜が属人化している` | — |
| ✅ 欠如系 | `〜が存在しない`, `〜がない`, `〜が未整備` | — |
| ✅ 品質系 | `〜が複雑すぎる`, `〜のカバレッジが低い`, `〜が理解しにくい` | — |
| ✅ 制約系 | `〜に対応できない`, `〜が制限される`, `〜でしか動かない` | — |
| ❌ Task形式 | `〜を設計する`, `〜を実装する`, `〜を追加する`, `〜を構築する`, `〜を改善する`, `〜に対応する`, `〜を修正する` | → Task/Story に変更すべき |
| ❌ 願望形式 | `〜したい`, `〜できるとよい` | → Needs の可能性 |
| ❌ 不具合形式 | `〜が動かない`, `〜でエラー` | → Bug の可能性 |

### 事実の種類を判定するキーワード

| 種類 | 検出パターン |
|------|------------|
| 記録 | `記録`, `ログ`, `データ`, `〜に記録`, `〜と表示`, `CI`, `メトリクス` |
| 直接の発言 | `〜が言った`, `〜と言った`, `〜が書いた`, `レトロで`, `MTGで` |
| 伝聞 | `〜から聞いた`, `〜によると`, `〜らしい`, `〜とのこと` |
| 観察 | `見た`, `観察した`, `確認した`, `私は〜を見た`, `気づいた` |

### 定量データの判定

| 判定 | パターン例 |
|------|----------|
| ✅ あり | `30分`, `週3回`, `2倍`, `50%増加`, `3人中1人` |
| ⚠️ 曖昧 | `時間がかかる`, `よく発生`, `多い` |
| ❌ なし | 数値に関する記載がない |

## 対話モード

`/pbi:check-tech` のみで実行した場合、対話形式で記載を促す：

```
📝 Tech Issue フォーマット入力モード

以下のテンプレートに沿って記載してください：

---
【Title】（課題形式で記載）
例: 〇〇がやりづらい / △△に時間がかかる / 🔳🔳さんしか作業できない

【事実】（以下から1つ以上選んで記載）

□ 記録: [いつ]、[システム/ツール名] に [こう記録されている]。
□ 発言: [いつ・どこで]、[誰] が [こう言った/書いた]。
□ 伝聞: [誰] から、[別の誰] が [こう言っていた] と聞いた。
□ 観察: [いつ・どこで]、私は [こうなっているの] を見た/聞いた。

💡 Tech Issueでは定量データ（時間、回数、頻度）を含めることを推奨

【解釈】
[この事実] から、[こういう意味だ] と私は読んでいる。
なぜなら [この事実] と [別の知識・事実・経験] を結びつけているからだ。
（ただし [別の結びつけ方] もありうる。）
---

入力してください:
> 
```

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 20点 | Status有効値・Owner設定・Owner×Status整合 |
| 構造チェック | 25点 | 事実・解釈セクションの存在 |
| フォーマット準拠 | 30点 | テンプレート形式への準拠度 |
| 整合性 | 25点 | 事実→解釈の論理的つながり、定量データ |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | Refinementに進めてOK |
| 60-79 | ⚠️ 要改善 | 指摘箇所を修正してから進める |
| 0-59 | ❌ 要リライト | テンプレートに沿って書き直し |

---

## 注意事項

- このAgentは**フォーマット準拠**を主眼としています
- 内容の妥当性（技術的に正しいか等）は判定しません
- Tech IssueはNeedsと異なり、**定量データ**の有無を重視します
- Title形式が「願望形式」や「不具合形式」の場合、Issue Type変更を提案します
