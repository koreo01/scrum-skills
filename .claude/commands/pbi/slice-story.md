# /pbi:slice-story — Story 縦スライス分割支援

ai-driven-development-style-guide §3.3（縦スライス）・§3.4（2トラック制）・§3.5（サブタスクのサイズ原則）に基づき、
Story を S0/S1/S2/S-final の縦スライスに分割します。

## コマンド形式

```
/pbi:slice-story [source]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `#NUMBER` | GitHub Issue 番号 | `#1234` |
| （省略） | 対話モード（Story内容を貼り付ける） | - |

> ℹ️ チケット ID フォーマットの実値は `.claude/config/ticket-system.json` の `ticketId` で定義する。他組織で流用する際は同 Config を書き換える。

---

## ワークフロー

### Step 1: Story の読み込み

ソース指定がある場合は `gh issue view` で Story を取得します。
省略時は Story のタイトルと受け入れ条件（Gherkin）・**Examples テーブル（具体値必須）** の入力を促します。
Examples テーブルがない、または変数名のみで具体値がない場合は警告を出し、Refinement への差し戻しを推奨します（check-story.md 項目11・項目18 参照）。

### Step 2: ウォーターフォール型分割の検出

受け入れ条件（Gherkin）または SubTask 候補に以下のパターンがないかを確認します。

**NG パターン（レイヤー別分割）の検出:**

| 検出パターン | 判定 |
|-------------|------|
| 「バックエンド: 〜」「フロントエンド: 〜」が別 SubTask に並ぶ | ❌ ウォーターフォール型 |
| 「設計」「API」「UI」「テスト」が別 SubTask に並ぶ | ❌ ウォーターフォール型 |
| フロントエンド完了後にバックエンド開始という依存関係がある | ❌ ウォーターフォール型 |
| 各 SubTask が単独では動作確認できない | ❌ ウォーターフォール型 |

NG パターンを検出した場合は警告を出力します（Step 3 で修正案を提示）。

### Step 3: 縦スライス分割案の生成

Story の受け入れ条件を分析して、S0/S1/S2/S-final に分割します。

---

## Refinement での Example Mapping 連携

縦スライス分割は **Refinement で Example Mapping が済んだ後** に行うのが理想。
Example Mapping で整理した具体例(Examples)がそのまま S1/S2/Sn の分割境界となる。
Examples の各行を **どの S で Green にするか** をマッピングすることで、スライスの粒度と E2E の成長レベル(L1→L3→L4→L5)が自然に連動する。

🔍 詳細: template-story.md の「Refinement で必ず行うこと」セクション

> **Examples が 6件以上の場合は Story 全体のスプリットを検討**（check-story.md 項目18）。
> ただし件数だけで判断せず、同一の仮説（同じ When で検証できる）かを確認する。
> 同一仮説のバリエーションなら件数が多くても同一 Story 内に留め、S1/S2/Sn に分解する。

## 縦スライスの設計原則

> **判断の最優先基準は「Sprint 内完走」**。INVEST の Independent/Valuable を理由に分割を躊躇しない。
> サブタスクのサイズ原則（§3.5）で各スライスが収まらないと判断したらためらわず分割する。
> エラーケース単位での価値は運用・セキュリティ・ユーザビリティの観点で十分に再確認されたい。

### スライス構造

```
S0（スケルトン）→ S1（ハッピーパス）→ S2〜Sn（異常系・追加ルール）→ S-final（仕上げ、任意）
```

各スライスは「その時点でCI が通り、動作確認できる状態」を保ちます。

### 各スライスの定義

| スライス | 目的 | 対応する Examples 行 | 目安工数 |
|---------|------|------------------|---------|
| **S0（スケルトン）** | DB マイグレーション + ルーティング骨格 + UI 骨格 + 最初の UT 1本（fail）| （該当なし: pending 状態） | 1セッション以内 |
| **S1（ハッピーパス）** | 正常系の一気通貫実装（UI〜DB まで動く状態） | Examples の正常系行を Green に | 1セッション以内 |
| **S2（異常系）** | エラー処理・バリデーション・セキュリティ対応 | Examples の異常系行を Green に | 1セッション以内 |
| **Sn（追加ルール）** | 追加の業務ルール・境界値・権限分岐 | Examples の境界値・追加ルール行を Green に | 1セッション以内（必要に応じて） |
| **S-final（仕上げ）** | リファクタ・E2E 安定化（任意） | （該当なし） | 1セッション以内 |

> **S2 で扱う「異常系」の定義**: 同一 Story の正常系(S1)と**同一の When（トリガー）**に対する異なる応答（エラー・バリデーション・追加ルール）を指す。
> When が異なる（別の操作・別のトリガー）場合は**同一 Story の S2 ではなく別 Story**として起票する。
> 詳細は `check-story.md` のエラーケース分割の判断軸 Layer 1 を参照。

### 2トラック制

各スライス内で以下の2トラックが並走します（§3.4）：

| トラック | 内容 |
|---------|------|
| **トラックA（機能実装）** | TDD（Red→Green→Refactor）で UT 主体の実装 |
| **トラックB（受け入れテスト）** | E2E テストを L0→L1→L3→L4→L5 の成長レベルで育てる |

## ウォーターフォール型の警告フォーマット

```
⚠️ ウォーターフォール型（レイヤー別）分割を検出しました。

検出されたパターン:
- {検出されたレイヤー別分割の内容}

この分割では {フロントエンドとバックエンドが別々に進み待ち時間が発生}
スウォーミング（§3.2）の効果が得られません。

縦スライス（価値単位）に組み替えます：
- NG: バックエンド API 実装 → フロントエンド UI 実装
- OK: S0 で UI・API・DB 骨格を同時作成 → S1 で正常系一気通貫
```

## 同一 When での Story 分割の警告フォーマット

```

- Story A の When: [振る舞い]（正常系のみ）
- Story B の When: [振る舞い]（異常系のみ）

When が同一であれば同一 Story の S1/S2 として実装すべきです。
Story B を Story A に統合し、S2（異常系）として扱ってください。

🔍 詳細: check-story.md 項目16・エラーケース分割の判断軸 Layer 1
```

## 参考: E2E テストの成長レベル（§3.4.2）

| レベル | 状態 | 到達タイミング |
|--------|------|-------------|
| L0 | Gherkin として記述済み | Story 起票時 |
| L1 | ラッパースクリプト作成（pending/skip） | **S0 完了時** |
| L2 | Selector・仮データで実行可能 | S1 途中 |
| L3 | ハッピーパス Green | **S1 完了時** |
| L4 | 異常系シナリオ追加 Green | S2 完了時 |
| L5 | 全シナリオ Green・安定 | S-final 完了時 |
