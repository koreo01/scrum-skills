# PBI Check Request Agent

Requestチケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-request [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/request-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のRequestチケットをチェック
/pbi:check-request #123

# チェック結果をファイルに保存
/pbi:check-request #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-request #123 --gh-comment

# 対話モード
/pbi:check-request
```

## Request Issue の特徴

Request Issueは**顧客からの依頼事項**（環境構築、設定変更など）を記録するIssueです。

### Title/Summary のパターン

| パターン | 例 |
|---------|-----|
| 〇〇様の環境構築依頼 | 「ABC株式会社様の環境構築依頼」 |
| △△の設定変更依頼 | 「XYZ社様のSSO設定変更依頼」 |
| 🔳🔳のデータ移行依頼 | 「DEF社様の旧システムからのデータ移行依頼」 |

### 他のIssue Typeとの違い

| 観点 | Needs | Tech | Bug | Request |
|------|-------|------|-----|---------|
| 起点 | 顧客の要望 | 開発者の課題 | 動作不良 | **顧客からの依頼** |
| 性質 | 機能改善 | 技術改善 | 不具合修正 | **作業依頼** |
| 重視 | 背景・解釈 | 定量データ | 再現手順 | **必要情報の完全性** |

### Statusライフサイクル

RequestはRequirementを経由せず、直接Taskに変換される（**Request→Task直行ルート**）。

```
Request → Triage → Refining → Story Defined（Task起票）→ In Sprint → Done
                                     ↑
                          Requirementは作成しない（直行ルート）
```

| Status | 意味 | Ownerの目安 |
|--------|------|------------|
| Triage | 受領・精査中 | Business |
| Refining | 依頼内容を確認・整理中 | Business |
| Story Defined | Taskに変換済み（Task起票完了） | Product |
| In Sprint | 対応作業中 | Product |
| Done | 依頼作業完了 | Product |

> **注意**: RequestはNeedsと異なり、Requirementを起票しない。依頼内容が整ったらTaskを直接起票する。

### Owner

| タイミング | Owner |
|-----------|-------|
| 起票〜Refining | Business |
| Task起票（Story Defined）以降 | Product |

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Triage / Refining / Story Defined / In Sprint / Done のいずれか |
| 0-2 | Ownerの設定 | Business または Product が設定されている |
| 0-3 | Owner×Statusの整合 | Triage・Refining は Business、Story Defined 以降は Product |
| 0-4 | Task直行ルートの確認 | Requirement（#xxx）が紐づいていない（Requestは直行ルートのため不要） |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | 依頼者情報の存在 | 会社名または担当者名の記載がある |
| 2 | 依頼内容の存在 | 何を依頼されているか明記されている |
| 3 | 期限情報の存在 | 希望納期または期限の記載がある |

### Phase 2: フォーマット準拠チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | Title形式 | 依頼形式（「〇〇様の△△依頼」等） |
| 5 | 会社名の明記 | 顧客の会社名が具体的に記載 |
| 6 | 期限の具体性 | 日付形式で記載（YYYY/MM/DD） |
| 7 | 成果物/完了条件 | 何をもって完了とするか明記 |

### Phase 3: 完全性チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 8 | 必要情報の網羅性 | 作業に必要な情報が揃っている |
| 9 | 連絡先の記載 | 確認が必要な場合の連絡先がある |
| 10 | 環境情報（該当時） | 環境構築の場合、環境詳細がある |
| 11 | 受領確認 | 依頼を受けた日時/経緯の記載 |

## 出力ファイル

### `--save` オプション使用時

出力先: `analysis/format-check/YYYY-MM-DD_<ticket-id>.md`

```markdown
# フォーマットチェック結果

- **チケット**: REQ-789「ABC株式会社様の環境構築依頼」
- **チェック日時**: 2026-04-01 21:30
- **スコア**: 70/100（⚠️ 要改善）

## 指摘事項

### ⚠️ 期限が不明確
- 箇所: 期限セクション
- 現在の記載: `なるべく早く`
- 対応: 具体的な日付（YYYY/MM/DD）で記載

### ⚠️ 必要情報が不足
- 不足: 管理者メールアドレス、初期ユーザー数
- 対応: 顧客に確認

### ❌ 受領確認なし
- 対応: 依頼を受けた日時と経緯を追記

## 次のアクション

1. [ ] 期限を具体的な日付で記載
2. [ ] 不足情報を顧客に確認
3. [ ] 依頼受領日を追記
4. [ ] 修正後に再度 `/pbi:check-request` で確認
```

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ 依頼形式 | `〇〇様の△△依頼`, `〇〇社の△△依頼`, `△△依頼（〇〇様）` |
| ❌ 願望形式 | `〜したい`（→ Needsの可能性） |
| ❌ 課題形式 | `〜がやりづらい`（→ Techの可能性） |
| ❌ 不具合形式 | `〜が動かない`（→ Bugの可能性） |

### 期限の判定

| 判定 | パターン |
|------|---------|
| ✅ 具体的 | `2026/04/15`, `4月15日`, `来週金曜日` |
| ⚠️ 曖昧 | `なるべく早く`, `急ぎ`, `今月中` |
| ❌ なし | 期限に関する記載がない |

### 必要情報の網羅性（環境構築の場合）

| 判定 | 含まれる情報 |
|------|------------|
| ✅ 完全 | 環境種別 + テナント名 + 管理者情報 + ユーザー数 |
| ⚠️ 不完全 | 一部のみ記載 |
| ❌ 不足 | 主要な情報が欠落 |

### 依頼種別の自動判定

| 依頼種別 | 検出キーワード | 追加チェック項目 |
|---------|--------------|-----------------|
| 環境構築 | `環境構築`, `テナント作成`, `新規導入` | 環境情報、管理者情報 |
| 設定変更 | `設定変更`, `SSO`, `IP制限` | 変更内容、影響範囲 |
| データ移行 | `データ移行`, `インポート`, `移行` | 移行元情報、データ形式 |
| アカウント | `アカウント`, `ユーザー追加`, `権限` | ユーザー情報、権限種別 |

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 20点 | Status有効値・Owner設定・Task直行ルート整合 |
| 構造チェック | 25点 | 依頼者・依頼内容・期限の存在 |
| フォーマット準拠 | 25点 | テンプレート形式への準拠度 |
| 完全性チェック | 30点 | 作業に必要な情報の網羅性 |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | 作業着手可能 |
| 60-79 | ⚠️ 要改善 | 不足情報を確認してから着手 |
| 0-59 | ❌ 要リライト | テンプレートに沿って書き直し |

## 注意事項

- このAgentは**フォーマット準拠と情報の完全性**を主眼としています
- 作業の実現可否や工数見積もりは判定しません
- Requestは**顧客対応**のため、情報の正確性が特に重要です
- 期限が曖昧な場合は必ず顧客に確認を促します
- 不足情報がある状態で作業着手すると手戻りのリスクがあります
- Title形式が他のIssue Typeに該当する場合、Issue Type変更を提案します
- **RequestはRequirementを経由しない。** Requirementが紐づいている場合はフロー誤りとして指摘する
- Statusが `Story Defined` なのに Owner が `Business` の場合は設定ミスとして指摘する
