# PBI Check Requirement Agent

Requirementチケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```bash
/pbi:check-requirement [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/req-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のRequirementチケットをチェック
/pbi:check-requirement #123

# チェック結果をファイルに保存
/pbi:check-requirement #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-requirement #123 --gh-comment

# 対話モード
/pbi:check-requirement
```

## 空・雨・傘における位置づけ

Requirement は「空・雨・傘」フレームワークの **雨（解釈）→ 傘（対応）の転換点** に位置します。

```text
空（事実）  ←── Needs「事実（空）」：観察・発言・記録などの生データ
雨（解釈）  ←── Needs「解釈（雨）」：事実から何を読み取るかの推論
     ↓ 解釈（雨）をもとに「何を解決するか」を定義する ← ここが Requirement
傘（対応）  ←── Requirement「解決内容」：雨（解釈）への具体的な対応策
     ↓ 対応策を仕様として展開する
Story       ←── 受け入れ条件（Gherkin形式）
```

**Requirementの役割**: Needs の雨（解釈）を受けて「**で、何をするか（傘）**」を定義する。
Why（空・雨）から What（傘の方向性）へ変換する層です。

## Requirement Issue の位置づけ

```text
Issue (Why)                    Requirement              Story/Task (What)
┌─────────┐                   ┌─────────────┐         ┌─────────────────────┐
│  Tech   │──(仕様変更あり)──→│             │────────→│ Story               │
│  Needs  │──(仕様変更あり)──→│ Requirement │         │ (Requirement Spec)  │
│  Bug    │──────────────────→│             │         └─────────────────────┘
└─────────┘                   └─────────────┘
```

**Requirement** = 「Why（なぜ困っているか）に対して **何を解決したいか（傘の方向性）** を記載」 = 要求・要件

### Title/Summary のパターン

| パターン | 例 |
|---------|-----|
| 〇〇を解決したい | 「予約変更の待ち時間を解決したい」 |
| △△ができるようにしたい | 「Webから予約変更ができるようにしたい」 |
| 🔳🔳を可能にしたい | 「セルフサービスでの日時変更を可能にしたい」 |

### 他のIssue Typeとの違い

| 観点 | Needs | Tech | Bug | **Requirement** |
|------|-------|------|-----|-----------------|
| 起点 | 顧客の要望 | 開発者の課題認識 | 動作不良の発見 | **Issue分析の結果** |
| Title形式 | 「〇〇したい」 | 「〇〇がやりづらい」 | 「〇〇が動かない」 | **「〇〇を解決したい」** |
| 必須情報 | 背景・解釈 | 背景・定量データ | 再現手順・環境 | **元Issue・解決内容** |
| 抽象度 | Why（なぜ困っている） | Why（なぜ困っている） | What（何が起きた） | **What（何を解決する）** |

## チェック対象テンプレート

### Requirementの必須要素

| フィールド | 必須事項 | 例 |
|-----------|---------|-----|
| **Title** | 「〜を解決したい」「〜ができるようにしたい」形式 | 「予約変更を電話なしでWeb完結できるようにしたい」 |
| **元Issue** | 派生元Issue（Tech/Needs/Bug）へのリンク | 【元Issue】NEEDS-100「予約変更が面倒で困っている」 |
| **解決内容** | 何を解決したいかの詳細 | ユーザーがWeb画面から予約日時を自分で変更できるようにする |
| **背景参照** | 元Issueの事実・背景への参照または補足 | 元Issue背景参照。追加制約: 変更可能期間は48時間前まで |

### 事実テンプレート（元Issueから継承）

元Issueの事実を参照または引用します：

```
【元Issueの事実】
[元Issue番号] より引用:
> [いつ]、[誰] が [こう言った/観察した]。
```

### 解決内容テンプレート

```
【解決したいこと】
[元Issueの困りごと] に対して、[こうすることで解決する]。

【達成条件】（任意・Gherkin形式推奨）
Given: [前提条件]
When: [操作]
Then: [期待結果]
```

### 補足テンプレート

```
【背景参照】
元Issue背景参照: [元Issue番号]

【追加制約】（あれば）
- [非機能要件: 応答時間、可用性等]
- [ビジネス制約: 変更可能期間、対象ユーザー等]
```

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Triage / Refining / Story Defined / In Sprint / Done のいずれか |
| 0-2 | Ownerの設定 | Business または Product が設定されている |
| 0-3 | Owner×Statusの整合 | Triage・Refining は Business、Story Defined 以降は Product |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | 元Issueリンク存在 | Needs/Tech/BugへのリンクまたはID記載がある |
| 2 | 解決内容の存在 | 「解決したいこと」「達成条件」等の記載がある |
| 3 | Title形式 | 解決意図形式（「〜を解決したい」「〜ができるようにしたい」） |

### Phase 2: フォーマット準拠チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | 元Issue番号の明記 | Issue番号（例: NEEDS-100, TECH-50）が記載 |
| 5 | Why→What変換 | 「困りごと」から「解決手段」への変換が明確 |
| 6 | 背景参照の有無 | 元Issueの背景・事実への参照がある |
| 7 | 抽象度の適切性 | Howに踏み込みすぎていない（実装詳細なし） |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 8 | 達成条件の記載 | Gherkin形式または具体的な完了条件 |
| 9 | 非機能要件の記載 | 性能・制約等の記載（該当する場合） |
| 10 | 検証可能性 | 「できた/できてない」が判断可能な記載 |
| 11 | Story展開可能性 | このRequirementからStoryに分解可能か |

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ 解決意図形式 | `〜を解決したい`, `〜ができるようにしたい`, `〜を可能にしたい`, `〜を実現したい` |
| ❌ 願望形式 | `〜したい`, `〜できるとよい`（→ Needsの可能性） |
| ❌ 課題形式 | `〜がやりづらい`, `〜に時間がかかる`（→ Techの可能性） |
| ❌ 不具合形式 | `〜が動かない`, `エラー`（→ Bugの可能性） |
| ❌ 実装形式 | `〜を実装する`, `〜APIを作成`, `〜機能`（→ Howへの踏み込み） |

### 元Issueリンクの判定

| 判定 | パターン |
|------|---------|
| ✅ 明確 | `NEEDS-123`, `TECH-456`, `BUG-789`, GitHub Issue リンク |
| ⚠️ 曖昧 | `関連Issue参照`, `別チケット参照` |
| ❌ なし | 元Issueへの参照がない |

### Why→What変換の判定

| 判定 | 状態 |
|------|------|
| ✅ 明確 | 「困りごと」と「解決手段」が明示的に記載 |
| ⚠️ 不明確 | 解決手段は書いてあるが困りごととの関連が不明 |
| ❌ なし | Why→Whatの変換が見えない |

### 抽象度の判定

| 判定 | パターン |
|------|---------|
| ✅ 適切（What） | 「〜できるようにする」「〜を可能にする」 |
| ⚠️ Howに近い | 「〜画面を作る」「〜ボタンを追加」 |
| ❌ How（実装詳細） | `React`, `API`, `DB`, 技術用語が多い |

### 達成条件の判定

| 判定 | パターン |
|------|---------|
| ✅ Gherkin形式 | `Given`, `When`, `Then` を使用 |
| ✅ 具体的 | 「〜した場合、〜となる」形式で記載 |
| ⚠️ 曖昧 | 「〜できる」のみ |
| ❌ なし | 達成条件の記載がない |

| Phase | 配点 | 評価観点 |
|-------|------|---------|

| スコア | 判定 | 推奨アクション |

## 良い例・悪い例

### 良い例 ✅

```markdown
# Title
予約変更を電話なしでWeb完結できるようにしたい

# 元Issue
【元Issue】NEEDS-100「予約変更が面倒で困っている」

# 解決したいこと
ユーザーがWeb画面から予約日時を自分で変更できるようにする。
現状は電話でのみ変更可能だが、営業時間内に電話できない
ユーザーが多く、変更を諦めるケースが発生している。

# 達成条件
Given: ユーザーが予約詳細画面を表示している
When: 日付を変更して「更新」ボタンを押す
Then: 予約が更新され、確認メールが送信される

# 背景参照
元Issue背景参照: NEEDS-100
顧客A社CS担当から「電話待ち30分」との声あり。
追加制約: チェックイン48時間前までの変更に限定する方針。
```

### 悪い例 ❌

```markdown
# Title
予約変更機能

# 解決したいこと
予約を変更できるようにする

# 達成条件
（空欄）
```

**問題点:**
- Title: 解決意図が不明確（「機能」という曖昧な表現）
- 元Issue: リンクなし（トレーサビリティ欠如）
- Why→What変換: 見えない
- 達成条件: 空欄（検証不可能）

---

## 注意事項

- このAgentは**フォーマット準拠**と**トレーサビリティ確保**を主眼としています
- 解決手段の妥当性（本当にこれで解決するか等）は判定しません
- 元Issueへのリンクは**必須**です（これがないとWhy→Whatの変換が追跡できない）
- 達成条件のGherkin形式は**強く推奨**です（検証可能性のため）
- 抽象度がHowに近い場合、Story化を検討するよう提案します
- Title形式が「願望形式」「課題形式」「不具合形式」の場合、Issue Type変更を提案します
