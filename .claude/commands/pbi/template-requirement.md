# PBI Template Requirement

check-requirement.md のチェックを通過しやすい Requirement チケットの雛形を出力します。

## コマンド形式

```
/pbi:template-requirement [--title "タイトル"]
```

| 引数 | 説明 |
|-----|------|
| `--title "タイトル"` | タイトルをあらかじめ埋めた状態で出力 |
| （省略） | 全フィールドが空欄の雛形を出力 |

---

## 使い方

> **議事録由来で作成する場合**: 先に `/pbi:invoke-story-ticket-helper` を実行してチケット候補を抽出してください。

1. このコマンドを実行すると、下記テンプレートを出力します
2. `[...]` で囲まれた部分を実際の内容に置き換えてください
3. 記載後に `/pbi:check-requirement` で品質確認してください

## 空・雨・傘における位置づけ

Requirement は「空・雨・傘」フレームワークの **雨（解釈）→ 傘（対応）の転換点** に位置します。

```text
空（事実）  ←── Needs「事実（空）」：観察・発言・記録などの生データ
     ↓ 事実をもとに意味を読み取る
雨（解釈）  ←── Needs「解釈（雨）」：事実から何を読み取るかの推論
     ↓ 解釈（雨）をもとに「何を解決するか」を定義する ← ここが Requirement
傘（対応）  ←── Requirement「解決内容」：雨（解釈）への具体的な対応策
     ↓ 対応策を仕様として展開する
Story       ←── 受け入れ条件（Gherkin形式）
```

**Requirementの役割**: Needs の雨（解釈）を受けて「**で、何をするか（傘）**」を定義する。
Why（空・雨）から What（傘の方向性）へ変換する層です。

## 出力テンプレート

以下のテンプレートをそのまま出力する：

```markdown
# [Requirementタイトル]
<!-- Title形式: 「〜を解決したい」「〜ができるようにしたい」「〜を可能にしたい」 -->
<!-- NG例: 「〜したい」（願望形式 → Needsに近い） / 「〜を実装する」（実装形式 → Howに踏み込み） -->
[困りごと]を[こうすることで]解決したい

## 元Issue
<!-- 必須: 派生元Issue（Needs/Tech/Bug）の#xxxまたはURLを記載 -->
【元Issue】[#xxx または URL]「[元Issueタイトル]」

## 解決したいこと
<!-- 必須: 元Issueの困りごとに対して何を解決するかを記載 -->
[元Issueの困りごと] に対して、[こうすることで解決する]。

## 達成条件
<!-- 推奨: Gherkin形式で記載 / 省略すると check-requirement.md で ⚠️ -->
Given: [前提条件]
When: [操作]
Then: [期待結果]

## 背景参照
<!-- 必須: 元Issueの背景・事実への参照 -->
元Issue背景参照: [#xxx]
<!-- 追加の事実・背景情報があれば記載 -->

## 追加制約（あれば）
<!-- 非機能要件・ビジネス制約など -->
- [非機能要件: 応答時間、可用性等]
- [ビジネス制約: 変更可能期間、対象ユーザー等]

## SubTask候補（任意）
- [ ] [SubTask1]
- [ ] [SubTask2]
```

## GitHub ラベル設定ガイド

| プロパティ | 値 | 設定タイミング |
|-----------|-----|-------------|
| Type | Requirement | 作成時 |
| Status | Triage | 起票時（調査・判断待ち） |
| Owner | Business | 起票〜Refiningまで（必須） |
| Status | Story Defined 以降 | ProductへOwner移行のタイミング |

### Owner × Status の整合ルール

| Status | Owner |
|--------|-------|
| Triage / Refining | Business |
| Story Defined 以降 | Product |

## check-requirement.md チェック項目との対応

| チェック項目 | テンプレートの対応箇所 |
|------------|----------------------|
| 0-1 Status有効値 | プロパティ設定ガイド参照 |
| 0-2 Owner設定 | プロパティ設定ガイド参照 |
| 0-3 Owner×Status整合 | Owner × Status の整合ルール参照 |
| 1 元Issueリンク存在 | `## 元Issue` セクション |
| 2 解決内容の存在 | `## 解決したいこと` セクション |
| 3 Title形式 | 1行目（「〜を解決したい」「〜ができるようにしたい」） |
| 4 元Issue番号の明記 | `【元Issue】#xxx` |
| 5 Why→What変換 | `## 解決したいこと`（困りごと→解決手段の対応） |
| 6 背景参照の有無 | `## 背景参照` セクション |
| 7 抽象度の適切性 | 「〜できるようにする」形式（Howに踏み込まない） |
| 8 達成条件の記載 | `## 達成条件`（Gherkin形式） |
| 9 非機能要件の記載 | `## 追加制約` セクション |
| 10 検証可能性 | 達成条件で「できた/できてない」が判断可能な記載 |
| 11 Story展開可能性 | 解決内容からStoryに分解できるか確認 |

## よくある記載ミス

| ミスのパターン | 正しい書き方 |
|-------------|------------|
| Title: 「予約変更機能」 | 「予約変更を電話なしでWeb完結できるようにしたい」（解決意図を明示） |
| Title: 「予約変更したい」 | 解決意図形式に変更。「したい」のみはNeedsに近い（Titleに使わない） |
| Title: 「予約変更APIを実装する」 | How（実装詳細）に踏み込んでいる。What（解決方向）に留める |
| 元Issueリンクなし | 必ず `【元Issue】#xxx` を記載（Whyとのトレーサビリティ必須） |
| 解決したいことが空欄 | 「[困りごと] に対して、[こうすることで解決する]」の形で記載 |
| 達成条件が「〜できる」だけ | Gherkin形式（Given/When/Then）で具体化する |
| 背景参照なし | `元Issue背景参照: #xxx` を必ず記載 |
| 「解決したいこと」にDB・APIなどの実装詳細 | 「何ができるようになるか」のWhat止まりで記載。Howは含めない |
