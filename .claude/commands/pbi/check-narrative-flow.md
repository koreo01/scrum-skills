# PBI Check Narrative Flow Agent

Narrative Flowチケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-narrative-flow [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/narrative-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のNarrative Flowチケットをチェック
/pbi:check-narrative-flow #123

# チェック結果をファイルに保存
/pbi:check-narrative-flow #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-narrative-flow #123 --gh-comment

# 両方（ファイル保存 + GitHub Issueコメント）
/pbi:check-narrative-flow #123 --save --gh-comment

# ローカルファイルをチェックして保存
/pbi:check-narrative-flow @docs/issues/user-onboarding-flow.md --save

# 対話モード
/pbi:check-narrative-flow
```

## Narrative Flow の位置づけ

```
Backbone（テーマ・大きな目標）
  └─ Narrative Flow（ユーザーシナリオの流れ）
       └─ Story（具体的な機能仕様・受け入れ条件）
            └─ SubTask（実装作業単位）
```

**Narrative Flow** = 「ユーザーが特定の目標を達成するまでの一連のシナリオの流れ」

Backboneが「何を実現するか（大テーマ）」を表すのに対し、Narrative Flowは「**そのテーマの中でユーザーがどう動くか（シナリオの粒度）**」を表す。配下のStoryが定義されることで具体的な仕様として展開される。

### Title/Summary のパターン

| パターン | 例 |
|---------|-----|
| 〇〇が△△するフロー | 「新規ユーザーが初回ログインからダッシュボード確認まで行うフロー」 |
| 〇〇から△△までの流れ | 「注文確定から配送完了通知受信までの流れ」 |
| 〇〇の△△シナリオ | 「管理者がユーザー権限を変更するシナリオ」 |

### Backbone / Story との違い

| 観点 | Backbone | **Narrative Flow** | Story |
|------|----------|--------------------|-------|
| 抽象度 | 最も高い（テーマ・エピック） | **中間（ユーザーシナリオ）** | 低い（具体的な機能仕様） |
| 主語 | 製品・サービス全体 | **特定のユーザー・ペルソナ** | ユーザー（受け入れ条件） |
| 記述内容 | 達成したい大目標・価値 | **ユーザーの行動シナリオの流れ** | Given/When/Then（Gherkin） |
| Storyリンク | 配下にNarrative Flowを持つ | **配下にStoryを持つ（必須）** | SubTaskに分解 |

## Statusライフサイクル・Owner

### Statusライフサイクル

Narrative Flowは「ビジネス部門向け」の計画アーティファクトであり、Storyのようなスプリント管理プロパティ（Workflow State等）は持たない。Statusは3段階のみ有効。

| Status | 意味 | Ownerの目安 |
|--------|------|------------|
| Refining | シナリオの流れを精査中 | Business |
| Story Defined | 配下のStoryが定義済み | Product |
| Done | 配下Storyがすべて完了 | Product |

### Owner

| タイミング | Owner |
|-----------|-------|
| Refining | Business |
| Story Defined 以降 | Product |

## チェック対象テンプレート

### Narrative Flowの必須要素

| フィールド | 必須事項 | 例 |
|-----------|---------|-----|
| **Title** | フロー/シナリオ形式（「〇〇が△△するフロー」等） | 「新規ユーザーが初回ログインからダッシュボード確認まで行うフロー」 |
| **概要** | このNarrative Flowが表すユーザーシナリオの要約 | 初めてサービスを利用するユーザーが... |
| **対象ユーザー** | このフローを辿るユーザーの属性・文脈 | 新規登録済みの一般ユーザー |
| **フロー概要** | ユーザーアクションの流れをステップで記述 | 1. ログイン画面を開く 2. ... |
| **親Backbone** | 起点となるBackboneへのリンク | #xxxx「ユーザーオンボーディング体験の改善」 |
| **配下Story** | 子Storyへのリンク（Story Defined以降は必須） | - #xxxx: 「ユーザーはメールアドレスでログインできる」 |

### Narrative Flowテンプレート

```
【概要】
[このNarrative Flowが表すユーザーシナリオの要約]

【対象ユーザー】
[このフローを辿るユーザーの属性・文脈]

【フロー概要】
1. [ステップ1: ユーザーアクション]
2. [ステップ2: ユーザーアクション]
3. [ステップ3: ユーザーアクション]

【親Backbone】
#xxxx: [Backboneのタイトル]

【配下Story】（Status=Story Defined以降は必須）
- [ ] #xxxx: [Story1のタイトル]
- [ ] #xxxx: [Story2のタイトル]
```

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Refining / Story Defined / Done のいずれか |
| 0-2 | Ownerの設定 | Business または Product が設定されている |
| 0-3 | Owner×Statusの整合 | Refining は Business、Story Defined 以降は Product |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | Title形式 | フロー/シナリオ形式（「〇〇が△△するフロー」「〇〇から△△まで」等） |
| 2 | 概要/目的の存在 | このNarrative Flowが表すシナリオの説明がある |
| 3 | 親Backboneリンク | 起点となるBackboneへの参照がある |

### Phase 2: フォーマット準拠チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | 配下Storyリンク | Status=Story Defined/Done の場合、子Storyへのリンクが1件以上ある |
| 5 | フロー概要（ステップ）の記載 | ユーザーアクションのステップが列挙されている |
| 6 | 対象ユーザー/起点の明示 | このフローを辿るユーザーの属性または文脈が記述されている |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 7 | ユーザー視点の一貫性 | フロー概要がユーザーの行動・体験として記述されている（実装詳細なし） |
| 8 | Story分解可能性 | このフローから Story に分解できる粒度になっている |
| 9 | Backbone との整合性 | このフローが親 Backbone のテーマに沿っている |

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ フロー/シナリオ形式 | `〜するフロー`, `〜から〜まで`, `〜のシナリオ`, `〜の流れ` |
| ❌ テーマ形式 | `〜の改善`, `〜の強化`（→ Backboneの可能性） |
| ❌ 機能形式 | `〇〇は△△できる`（→ Storyの可能性） |
| ❌ 作業形式 | `〜を実装する`（→ Task/SubTaskの可能性） |

### 配下Storyリンクの判定

| Status | 判定 | ルール |
|--------|------|--------|
| Refining | ⚠️ 推奨 | なくても問題ないが追加を推奨 |
| Story Defined | ❌ 必須 | 1件以上のStoryリンクが必要 |
| Done | ❌ 必須 | 1件以上のStoryリンクが必要 |

### フロー概要（ステップ）の具体性判定

| 判定 | パターン例 |
|------|----------|
| ✅ 具体的 | 「ログイン画面でメールアドレスとパスワードを入力する」 |
| ⚠️ 曖昧 | 「ログインする」「確認する」「操作する」 |
| ❌ なし | ステップの記載がない |

### ユーザー視点の判定（フロー概要内）

| 判定 | パターン |
|------|---------|
| ✅ ユーザー視点 | ユーザーのアクション・体験として記述されている |
| ❌ 実装詳細混入 | `APIを呼ぶ`, `DBを更新する`, `バックエンドが処理する` |
| ❌ システム視点 | 「システムが〜する」「処理が〜される」のみで記述されている |

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 20点 | Status有効値・Owner設定・Owner×Status整合 |
| 構造チェック | 30点 | Title形式・概要/目的・親Backboneリンク |
| フォーマット準拠 | 30点 | 配下Storyリンク・フロー概要・対象ユーザー |
| 品質チェック | 20点 | ユーザー視点一貫性・Story分解可能性・Backbone整合 |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | Story化・Story Definedへの移行OK |
| 60-79 | ⚠️ 要改善 | 指摘箇所を修正してから進める |
| 0-59 | ❌ 要リライト | テンプレートに沿って書き直し |

## 良い例・悪い例

### 良い例 ✅

```markdown
# Title
新規ユーザーが初回ログインからダッシュボード確認まで行うフロー

# 概要
サービスに新規登録したユーザーが、初めてシステムにログインしてダッシュボードで
主要指標を確認するまでの一連の体験フロー。

# 対象ユーザー
新規登録済みの一般ユーザー（初回ログイン前）

# フロー概要
1. メールに届いた招待リンクをクリックしてログイン画面を開く
2. メールアドレスとパスワードを入力してログインする
3. ウェルカム画面でチュートリアルを確認する
4. メインダッシュボードで担当案件のサマリーを確認する

# 親Backbone
#1200: 「ユーザーオンボーディング体験の改善」

# 配下Story
- [ ] #1210: 「ユーザーは招待メールのリンクからログイン画面に遷移できる」
- [ ] #1211: 「ユーザーはメールアドレスとパスワードでログインできる」
- [ ] #1212: 「ユーザーは初回ログイン後のウェルカム画面でチュートリアルを確認できる」
- [ ] #1213: 「ユーザーはダッシュボードで担当案件のサマリーを確認できる」
```

### 悪い例 ❌

```markdown
# Title
ログイン機能

# 概要
ログイン関連の実装。

# フロー概要
1. APIを呼ぶ
2. DBを確認する
3. 画面を表示する
```

**問題点:**
- Title: 機能名称（Storyまたは実装Taskの可能性）
- 概要: ユーザーシナリオではなく実装の説明になっている
- フロー概要: 実装詳細（API・DB）になっており、ユーザー視点がない
- 親Backboneリンク: なし
- 対象ユーザー: なし

---

## 注意事項

- このAgentは**フォーマット準拠**を主眼としています
- シナリオの妥当性（本当にこのフローで良いか等）は判定しません
- **配下StoryリンクはStory Defined以降で必須**: Refining 時点では推奨、Story Defined に移行する前に必ず追加すること
- **フロー概要はユーザー視点で記述**: 実装詳細（API・DB・バックエンド処理）はNarrative Flowに含めない
- **Workflow StateはNarrative Flowには存在しない**: Story/Task/SubTaskのみのプロパティ
- **Status は3段階のみ有効**: Triage・Refining（全5段階中の2番目）ではなく、Narrative Flow固有の3段階（Refining/Story Defined/Done）
- Title形式がテーマ形式（「〜の改善」等）の場合、Backbone化を提案します
- Title形式が機能形式（「〇〇は△△できる」）の場合、Story化を提案します
