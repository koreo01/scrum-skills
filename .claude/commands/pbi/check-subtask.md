# PBI Check SubTask Agent

SubTaskチケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-subtask [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/subtask-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のSubTaskチケットをチェック
/pbi:check-subtask #123

# チェック結果をファイルに保存
/pbi:check-subtask #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-subtask #123 --gh-comment

# 対話モード
/pbi:check-subtask
```

## SubTask の位置づけ

SubTaskは「**具体的に何をコミットするか**」を定義する最小作業単位。Story またはTaskの子チケットとして必ず紐づく。

```
【Story配下のSubTask】
Story (What Specified)
  └─ SubTask  ← 「フロントエンドの実装」「APIの追加」等、1コミット相当の作業
       └─ コミット: [#{StoryID}/#{SubTaskID}] 〇〇を実装する

【Task配下のSubTask】
Task (作業定義)
  └─ SubTask  ← 「設定変更」「テスト追加」等、1コミット相当の作業
       └─ コミット: [#{TaskID}/#{SubTaskID}] 〇〇を実装する
```

> ℹ️ コミットメッセージのフォーマット実値は `.claude/config/ticket-system.json` の `commitMessage.formats` で定義する。他組織で流用する際は同 Config を書き換える。

**SubTask** = 「1コミット相当の具体的作業」。親Story/Taskのスコープを分割した作業単位。

### Statusライフサイクル

SubTaskのStatusは4ステータスのみ有効（Refining/Refined は SubTask に存在しない）。

```
To Do → In Progress → Reviewing → Done
```

| Status | 意味 |
|--------|------|
| To Do | 起票直後・着手前 |
| In Progress | 作業中 |
| Reviewing | PRレビュー中 |
| Done | mainマージ完了 |

### 親チケットリンク（必須）

SubTaskには必ず親Story/Taskの#xxxを本文に `Parent: #xxx` として記載する（GitHub Issues にはリレーションフィールドが無いため、本文記法で表現する）。`【親Task/Story】#xxx` の形での参照も併記することを推奨。

| 項目 | 設定場所 | 必須度 |
|------|---------|-------|
| 親チケット（本文記法 `Parent: #xxx`） | 本文冒頭 | ⭐ 必須 |
| 親チケット参照（本文） | 本文の背景/目的セクション | 推奨 |

### Title/Summary のパターン

SubTaskのTitleは「具体的な作業内容」を端的に表す。Story/Taskより細粒度の実装単位を示す。

| パターン | 例 |
|---------|-----|
| 〇〇を実装する | 「予約変更APIエンドポイントを実装する」 |
| 〇〇を追加する | 「変更期限チェックロジックを追加する」 |
| 〇〇を修正する | 「タイムアウト設定を修正する」 |
| 〇〇を追加/更新する | 「E2Eテストを追加する」 |
| 〇〇の設定変更 | 「本番環境のSSO設定変更」 |

### 他のチケット Typeとの違い

| 観点 | Task | **SubTask** |
|------|------|-------------|
| 起点 | Request直行 or Issue系保守 | **Story/Task分解** |
| Title形式 | 「〇〇を〇〇する」（作業まとまり） | **「〇〇を実装する」（具体的実装単位）** |
| 完了条件 | DoD形式（完了条件を列挙） | **コミット完了で判定（シンプルな完了基準）** |
| 粒度 | 1ブランチ相当の作業まとまり | **1コミット相当の作業単位** |
| 親チケット設定 | 任意（元Request/Issue参照） | **必須（`type:subtask` ラベル + 本文の `Parent: #xxx`）** |

## チェック対象テンプレート

### SubTaskの必須要素

| フィールド | 必須事項 | 例 |
|-----------|---------|-----|
| **Type** | SubTask（`type:subtask` ラベル） | type:subtask |
| **親チケット** | 親Story/Taskの#xxx（本文記法 `Parent: #xxx`） | Parent: #1100 |
| **Title** | 具体的な作業形式（「〇〇を実装する」等） | 「予約変更APIを実装する」 |
| **作業内容** | 何をどう実装するか | 変更内容の概要 |
| **完了基準** | このSubTaskが完了したと判断できる条件 | コミット・テストパス等 |

### SubTaskテンプレート

```
【親Task/Story】#xxx（タイトル）

【作業内容】
[このSubTaskで具体的に何をするか]

【完了基準】
- [ ] [完了条件1（コミット可能な状態）]
- [ ] [完了条件2]

【依存関係】（任意）
- 先行: #xxx（〇〇が完了してから着手）
- 後続: #xxx（このSubTask完了後に着手）
```

## チェックルール

### Phase 0: プロパティチェック

GitHub Issue のラベル・本文記法（Status ラベル / Workflow State ラベル / 親Issue参照）の設定が正しいかを確認する。

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | To Do / In Progress / Reviewing / Done のいずれか（Refining/Refined は SubTask に無効） |
| 0-2 | 親チケットの設定 | 本文に `Parent: #xxx` が記載されている |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | Title形式 | 具体的な作業形式（「〇〇を実装する」「〇〇を追加/修正する」等） |
| 2 | 親チケット参照 | 本文に親Task/Storyの#xxxへの参照がある（または 本文の `Parent: #xxx` 記載で確認可） |
| 3 | 作業内容の存在 | 何をどう実装するかの説明がある |
| 4 | 完了基準の存在 | このSubTaskが完了したと判断できる条件が記載されている |

### Phase 2: 完了基準チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 5 | 完了基準の具体性 | 「〜が実装されている」「〜テストがパスしている」等、客観的に判定可能 |
| 6 | 1コミット相当か | 作業範囲が1コミットに収まる規模感（過大でも過小でもない） |
| 7 | 実施可能性 | 先行依存（未完了SubTask）がある場合、その依存関係が明示されている |
| 8 | 曖昧表現なし | 「適切に」「正しく」等の主観的表現がない |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 9 | 単一責任 | 1つのSubTaskが1つの作業単位に対応 |
| 10 | 作業範囲の明確性 | 何がスコープ内で何が外かが判断できる |
| 11 | 親チケットとの整合性 | 親Task/Storyの完了条件・受け入れ条件と紐づいている |

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ 具体的作業形式 | `〇〇を実装する`, `〇〇を追加する`, `〇〇を修正する`, `〇〇のテストを追加する` |
| ❌ ユーザーストーリー形式 | `〇〇は△△できる`（→ Storyの可能性） |
| ❌ 作業まとまり形式（大きすぎ） | `〇〇機能全体を開発する`（→ Task化を提案） |
| ❌ 不具合形式 | `〜が動かない`, `〜がおかしい`（→ Bug Issue化を提案） |

### 完了基準の判定

| 判定 | パターン |
|------|---------|
| ✅ 具体的 | 「〜が実装されている」「〜テストがパスしている」「〜が設定されている」 |
| ⚠️ 曖昧 | 「動作すること」「完成していること」 |
| ❌ なし | 完了基準の記載がない |

### 作業規模の判定

| 判定 | 基準 |
|------|------|
| ✅ 適切（1コミット相当） | 単一ファイルの変更、単一機能の追加、単一バグ修正 |
| ⚠️ 過大 | 複数の独立した機能実装を含む（→ 複数SubTaskへの分割を提案） |
| ⚠️ 過小 | 1行の変更等、単独コミットにする意味が薄い（→ 他SubTaskとの統合を提案） |

### 曖昧表現の検出

| 検出パターン | 改善例 |
|-------------|--------|
| `正しく〜される` | 具体的な状態・結果を記載 |
| `適切に〜する` | 何がどうなれば適切かを記載 |
| `問題なく〜` | 成功条件を具体的に記載 |
| `〜こと` のみ | 判定可能な条件を追加 |

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 20点 | Status・親チケット設定 |
| 構造チェック | 25点 | Title形式・親チケット参照・作業内容・完了基準の存在 |
| 完了基準チェック | 30点 | 具体性・1コミット相当か・実施可能性・曖昧表現なし |
| 品質チェック | 25点 | 単一責任・作業範囲の明確性・親チケットとの整合性 |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | 作業着手可能 |
| 60-79 | ⚠️ 要改善 | 指摘箇所を修正してから着手する |
| 0-59 | ❌ 要リライト | 親Task/StoryのDoD・受け入れ条件から書き直し |

## 良い例・悪い例

### 良い例 ✅

```markdown
# Title
予約変更APIエンドポイントを実装する

# 親Task/Story
【親Story】#1050「ユーザーはWeb画面から予約日時を変更できる」

# 作業内容
PUT /reservations/{id} エンドポイントを実装する。
- リクエストボディで新しいチェックイン日時を受け付ける
- 変更期限チェック（チェックイン48時間前まで）を適用する
- 変更成功時はレスポンスに更新後の予約情報を返す

# 完了基準
- [ ] PUT /reservations/{id} エンドポイントが実装されている
- [ ] 変更期限チェックロジックが動作し、期限超過時に 422 エラーを返す
- [ ] 単体テストが追加されパスしている（正常系・異常系）
- [ ] コードレビューが完了している

# 依存関係
- 先行: #1051（変更期限チェックロジック追加）が完了してから着手
```

### 悪い例 ❌

```markdown
# Title
API対応

# 作業内容
予約変更APIを作る

# 完了基準
動作すること
```

**問題点:**
- Title: 何のAPIか不明（「API対応」では作業範囲が不明瞭）
- 親チケット: なし（どのStory/Taskの作業かわからない）
- 作業内容: 「作る」では何をどう実装するか不明
- 完了基準: 「動作すること」は曖昧。客観的に判定できない

## 注意事項

- このAgentは**フォーマット準拠と完了基準の品質**を主眼としています
- 実装の技術的妥当性（その方法で実現できるか等）は判定しません
- **SubTaskの `Type: SubTask` 設定は必須**: GitHub Issue のラベルで `type:subtask` になっていること。別DBのST-xxx形式は廃止済み
- **親チケット設定は必須**: SubTaskは必ず親Story/Task（#xxx）に紐づく。親チケット未設定のSubTaskはスタンドアロンで存在できない
- **SubTaskは4ステータスのみ有効**: Refining/Refined は Issue・Task など上位チケット専用。SubTask に設定された場合は即指摘する
- **1コミット相当の粒度を維持**: SubTaskが大きすぎる場合（複数の独立した実装を含む）は、複数SubTaskへの分割を提案する
- **SubTaskにGherkin形式は不要**: SubTask完了の判定は完了基準の達成で行う。GherkinはStoryの受け入れ条件として親Storyに記載する
- **コミットメッセージとの対応**: SubTaskは `[#{親ID}/#{SubTaskID}] 説明` 形式のコミット1件に対応する設計
- Title形式が「ユーザーストーリー形式」の場合、Story化を提案します
- Title形式が「作業まとまり形式（大きすぎ）」の場合、Task化を提案します
