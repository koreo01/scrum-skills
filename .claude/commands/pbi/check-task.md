# PBI Check Task Agent

Taskチケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-task [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/task-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のTaskチケットをチェック
/pbi:check-task #123

# チェック結果をファイルに保存
/pbi:check-task #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-task #123 --gh-comment

# 対話モード
/pbi:check-task
```

## Task の位置づけ

Taskは「**何をするか**」を定義する作業チケット。2つの起点がある。

```
【起点1: Request→Task直行ルート】
Request → Triage → Refining → Story Defined（Task起票）→ In Sprint → Done
                                   ↑
                          Requirementは作成しない（直行ルート）

【起点2: Issue→Task ルート】
Issue (Tech/Needs/Bug)  → Requirement → Story
                       └─────────────────→ Task  ← 仕様化が不要な保守・技術的作業
```

**Task** = 「作業の定義」。保守・CI改良・設定変更・リファクタ・ドキュメント等、Storyにならない作業を担う。

### Statusライフサイクル

TaskのStatusは6ステータスが有効。SubTaskと異なり、Refining / Refined を使用する。

```
To Do → Refining → Refined → In Progress → Reviewing → Done
```

| Status | 意味 |
|--------|------|
| To Do | 起票直後・着手前 |
| Refining | 議論・精査中 |
| Refined | 設計確定・SubTask分解可能な状態 |
| In Progress | 作業中（SubTask展開中） |
| Reviewing | PRレビュー中 |
| Done | mainマージ完了 |

### Planned Release Version / Released Version

| プロパティ | 設定タイミング | 必須度 |
|-----------|-------------|-------|
| Planned Release Version | Status が In Progress に移行した時点 | ⭐ 必須 |
| Released Version | Status が Done になった時点（Resolution=Implemented/Fixed の場合必須） | ⭐ Done後必須 |

### Title/Summary のパターン

| パターン | 例 |
|---------|-----|
| 〇〇を〇〇する | 「CI/CDパイプラインを整備する」 |
| 〇〇の△△対応 | 「本番環境のSSO設定変更対応」 |
| 〇〇の△△追加/修正 | 「デプロイスクリプトのタイムアウト設定を修正する」 |

### 他のチケット Typeとの違い

| 観点 | Story | **Task** | SubTask |
|------|-------|----------|---------|
| 起点 | Requirement分解 | **Request直行 or Issue系保守** | Task/Story分解 |
| Title形式 | 「〇〇は△△できる」 | **「〇〇を〇〇する」（作業形式）** | 「〇〇を実装する」等 |
| 完了条件 | Gherkin形式（必須） | **DoD形式（完了条件を列挙）** | タスク完了で判定 |
| 粒度 | 1スプリント以内で完了できる機能 | **1ブランチ相当の作業まとまり** | 1コミット相当の作業単位 |

## チェック対象テンプレート

### Taskの必須要素

| フィールド | 必須事項 | 例 |
|-----------|---------|-----|
| **Title** | 作業形式（「〇〇を〇〇する」等） | 「本番環境のSSO設定を変更する」 |
| **背景/目的** | なぜこのTaskが必要か | 【背景】顧客からの依頼（#xxx参照） |
| **完了条件** | 何をもって完了とするか（列挙形式） | - [ ] SSO設定が有効化されている |
| **元チケット** | 起点となるRequestまたはIssueへのリンク | 【元Request】#xxx |

### Taskテンプレート

```
【背景/目的】
[なぜこのTaskが必要か。元RequestまたはIssueのリンク]

【作業内容】
[具体的に何をするか]

【完了条件】
- [ ] [完了条件1（客観的に判定可能な項目）]
- [ ] [完了条件2]
- [ ] [完了条件3]

【SubTask候補】（任意）
- [ ] [SubTask1]
- [ ] [SubTask2]
```

## チェックルール

### Phase 0: プロパティチェック

GitHub Issue のラベル（Status / Workflow State / Release Version）の設定が正しいかを確認する。

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | To Do / Refining / Refined / In Progress / Reviewing / Done のいずれか |
| 0-2 | Planned Release Versionの設定 | Status が In Progress 以降の場合、必須設定されている |
| 0-3 | Released Versionの設定 | Status が Done かつ Resolution=Implemented/Fixed の場合、設定されている |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | Title形式 | 作業形式（「〇〇を〇〇する」「〇〇の△△対応」等） |
| 2 | 背景/目的の存在 | なぜこのTaskが必要かの説明がある |
| 3 | 完了条件の存在 | 「完了条件」または「DoD」の記載がある |

### Phase 2: 完了条件チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | 完了条件の具体性 | 「〜が設定されている」「〜が動作する」等、客観的に判定可能 |
| 5 | 完了条件の網羅性 | 主要な作業項目が揃っている |
| 6 | 曖昧表現なし | 「適切に」「正しく」等の主観的表現がない |
| 7 | 元チケットリンク | 起点となるRequest/Issueの#xxxへの参照がある |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 8 | SubTask分解可能性 | このTaskからSubTaskに分解可能か |
| 9 | 単一責任 | 1つのTaskが1つの作業まとまりに対応 |
| 10 | 作業範囲の明確性 | 何がスコープ内で何が外かが判断できる |
| 11 | 見積もり可能性 | 作業内容から工数の大枠が把握できる |

## 出力ファイル

### `--save` オプション使用時

出力先: `analysis/format-check/YYYY-MM-DD_<ticket-id>.md`

- **スコア**: 80/100（⚠️ 要改善）

## 指摘事項

### ⚠️ 完了条件に曖昧表現あり
- 箇所: 完了条件
- 現在の記載: `SSOが正しく動作すること`
- 対応: 具体的な判定条件（観察可能な結果）に書き換える

### ⚠️ 元チケットリンクなし
- 対応: 元Requestの#xxxを本文に追記

## 次のアクション

1. [ ] 完了条件を具体化
2. [ ] 元チケットリンクを追記
3. [ ] 修正後に再度 `/pbi:check-task` で確認

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ 作業形式 | `〇〇を〇〇する`, `〇〇の△△対応`, `〇〇を追加/修正/削除する` |
| ❌ ユーザーストーリー形式 | `〇〇は△△できる`（→ Storyの可能性） |
| ❌ 願望形式 | `〜したい`（→ Needsの可能性） |
| ❌ 不具合形式 | `〜が動かない`, `〜がおかしい`（→ Bugの可能性） |

### 完了条件の判定

| 判定 | パターン |
|------|---------|
| ✅ 具体的 | 「〜が設定されている」「〜が動作することを確認済み」「〜テストがパスしている」 |
| ⚠️ 曖昧 | 「正しく動作する」「適切に設定する」「問題なく使えること」 |
| ❌ なし | 完了条件の記載がない |

### 曖昧表現の検出

| 検出パターン | 改善例 |
|-------------|--------|
| `正しく〜される` | 具体的な状態・結果を記載 |
| `適切に〜する` | 何がどうなれば適切かを記載 |
| `問題なく〜` | 成功条件を具体的に記載 |
| `〜こと` のみ | 判定可能な条件を追加 |

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 20点 | Status・Planned Release Version・Released Versionの設定 |
| 構造チェック | 25点 | Title形式・背景目的・完了条件の存在 |
| 完了条件チェック | 30点 | 具体性・網羅性・元チケットリンク |
| 品質チェック | 25点 | SubTask分解可能性・単一責任・作業範囲の明確性 |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | スプリント投入可能（SubTask分解へ） |
| 60-79 | ⚠️ 要改善 | 指摘箇所を修正してから進める |
| 0-59 | ❌ 要リライト | テンプレートに沿って書き直し |

## 良い例・悪い例

### 良い例 ✅

```markdown
# Title
本番環境のSSO設定を変更する

# 背景/目的
【元Request】#1100「ABC株式会社様のSSO設定変更依頼」に基づく対応。
現在の設定では対象ユーザーがシングルサインオンできない状態。

# 作業内容
- テナント設定画面でSSOプロバイダーをOktaに切り替える
- SAML設定値を顧客提供の証明書で更新する
- テスト用アカウントで動作確認を行う

# 完了条件
- [ ] 対象テナントのSSOプロバイダーがOktaに設定されている
- [ ] 顧客提供のSAML証明書が登録されている
- [ ] テスト用アカウントでSSOログインが成功し、ダッシュボードにリダイレクトされることを確認済み
- [ ] 顧客に完了報告済み

# SubTask候補
- [ ] #xxxx: テナント設定変更（SSO有効化）
- [ ] #xxxx: SAML証明書の更新
- [ ] #xxxx: 動作確認・顧客報告
```

### 悪い例 ❌

```markdown
# Title
SSO対応

# 作業内容
SSOをOktaに変更する

# 完了条件
SSOが正しく動作すること
```

**問題点:**
- Title: 主語・動詞が不明確（何の・何を・どうする？）
- 背景/目的: なし（なぜやるかが不明）
- 完了条件: 「正しく動作すること」は曖昧。客観的に判定できない
- 元チケットリンク: なし（トレーサビリティ欠如）

## 注意事項

- このAgentは**フォーマット準拠と完了条件の品質**を主眼としています
- 作業の技術的妥当性（その方法で実現できるか等）は判定しません
- **TaskにはGherkin形式の受け入れ条件は不要**: Story（機能仕様）とは異なり、Taskは「完了条件」の列挙形式を使う
- **Planned Release Versionは In Progress 移行時点で必須**: 未設定のまま In Progress になっている場合は指摘する
- **Released Versionは Done 後に設定（Resolution=Implemented/Fixed の場合）**: Done になってリリースが完了したら必ず設定すること
- **Request→Task直行ルート**: Requestに紐づくTaskにはRequirementは存在しない。元Requestの#xxxをリンクするだけでよい
- Title形式が「ユーザーストーリー形式」の場合、Story化を提案します
- Title形式が「不具合形式」の場合、Bug Issue化を提案します
