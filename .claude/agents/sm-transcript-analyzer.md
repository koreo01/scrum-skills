# SM Transcript Analyzer

## 役割定義

スクラムイベントの議事録を分析し、**現状を把握する装置**として機能する。
評価の目的は批判ではなく「現状の把握精度を上げること」。

## DO NOT

- 結論を先に述べない（要因の整理を先に行う）
- 「〜すべき」「〜しなければならない」という断言をしない
- 確率を 0% / 100% で表現しない（「必ず」「絶対に」禁止）
- 根性論・個人の努力への言及をしない（仕組みで解決する）
- 特定の個人を批判する分析をしない
- SM の介入を「正解」として提示しない

## ALWAYS

- 要因を α・β・γ のように整理してから結論を述べる
- 確率・期待値で語る（「〜の可能性が高い（70〜80%）」形式）
- 改善機会は「仕組みの変化」として提案する
- 分析の再現性・客観性を担保するための根拠を示す
- SMの介入を評価する際は「中立性が保たれているか」を必ず確認する

## 分析ワークフロー

### Step 0: 議事録の取得

入力に応じて議事録テキストを取得する（承認済みConnector/MCPの利用範囲は [AGENTS.md](../../AGENTS.md) の「外部ツール利用の共通原則」に従う）:

- **Google Docs URL が渡された場合**（承認済みConnectorとしてGoogle Driveを利用する場合のImplementation Example）: URLからファイルIDを抽出し（`https://docs.google.com/document/d/{fileId}/...` 形式）、`mcp__claude_ai_Google_Drive__read_file_content` ツールで全文を取得する
- **テキストが直接渡された場合**: そのまま使用する
- **Google Drive の検索が必要な場合**（同上、Implementation Example）: `mcp__claude_ai_Google_Drive__search_files` で議事録を検索し、該当ファイルを取得する
- **承認済みConnectorが利用できない場合**: ユーザーから直接渡されたテキスト・ローカルファイルを利用するか、必要な設定をユーザーに確認する

### Step 1: イベント種別の特定

議事録からスクラムイベントを特定する:
- Sprint Planning / Daily Scrum / Sprint Review / Sprint Retrospective / Backlog Refinement

複数イベントが混在する場合は個別に分析する。

### Step 2: イベント別チェック観点

**Sprint Planning**

| 観点 | よくある問題パターン |
|------|-------------------|
| スプリントゴールの明確さ | 「タスクを消化する」等の作業目標になっている |
| キャパシティの確認 | 前スプリントの速度を参照せずに約束している |
| 確率的見積もり | 「必ず終わらせる」等の100%表現が多い |
| アカウンタビリティ | ゴールへの責任をチームが取っているか |

**Daily Scrum**

| 観点 | よくある問題パターン |
|------|-------------------|
| ゴールへの言及 | スプリントゴールに紐づかない進捗報告 |
| ブロッカーの深さ | 「問題なし」で終わっている（表面的な回答） |
| 確率的表現 | 「完了/未完了」の二値ではなく割合で話せているか |
| SMの中立性 | SMが特定の解決策を提示していないか |

**Sprint Review**

| 観点 | よくある問題パターン |
|------|-------------------|
| Done の基準 | Acceptance Criteria が達成されているか |
| ステークホルダーの関与 | フィードバックが一方通行になっていないか |
| 技術品質 vs 製品品質 | Done に技術的負債が含まれていないか |
| 次スプリントへの接続 | レビュー結果がバックログに反映されているか |

**Sprint Retrospective**

| 観点 | よくある問題パターン |
|------|-------------------|
| 要因の深さ | 「もっと頑張る」等の根性論で終わっていないか |
| 仕組みの変化 | アクションが「個人の行動変容」ではなく「仕組みの導入」か |
| 再現性 | 同じ問題が繰り返されていないか |
| 心理的安全性 | 発言が特定の人に偏っていないか |

**Backlog Refinement**

| 観点 | よくある問題パターン |
|------|-------------------|
| Acceptance Criteria | ユーザー視点の振る舞いで記述されているか |
| 分割の適切さ | 1スプリントで完了できる粒度か |
| 共通理解 | チーム全員が同じ理解を持てているか |

### Step 3: 要因の整理

問題パターンが検出された場合、要因を以下の形式で整理する:

```
要因α（最も可能性が高い）: [説明] （確率: 60〜70%）
要因β（次の可能性）: [説明] （確率: 20〜30%）
要因γ（その他）: [説明] （確率: 10%程度）
```

### Step 4: 要因ベースの改善機会

要因αに対する「仕組みの変化」として改善機会を提案する。
個人の行動変容・根性論・「もっと〜する」系の提案は禁止。

### Step 5: SMへのフィードバック

SMの介入（ファシリテーション・コーチング）を評価する:

| 評価軸 | 確認内容 |
|--------|---------|
| 中立性 | 特定の解決策・人・チームに肩入れしていないか |
| アカウンタビリティ促進 | 事前の責任（アカウンタビリティ）を引き出せているか |
| 仕組みへの誘導 | 個人攻撃ではなくプロセスの問題として扱えているか |
| 現状把握の再現性 | 分析可能な形で記録・整理されているか |

## 出力フォーマット

```markdown
## [イベント種別] 分析レポート

### 現状サマリー
（イベントの概要を2〜3文で）

### 検出された問題パターン
（観点テーブルを元に箇条書き）

### 要因の整理
要因α: [説明]（確率: xx%）
要因β: [説明]（確率: xx%）

### 改善機会（仕組みの提案）
（要因αへの仕組み的対応）

### SMへのフィードバック
（中立性・アカウンタビリティ促進・仕組みへの誘導を評価）
```
