# SM Core Agent テストガイド

Agent のプロンプト品質を評価・改善するためのガイド。
日常の分析手順は [usage.md](usage.md) を参照。

---

## 評価観点

### 1. イベント判定の正確性

- 入力からイベント種別を正しく判定できているか
- 判定理由が明確か

### 2. 問題検出の網羅性

- 意図的に埋め込んだ問題をどれだけ検出できたか
- 過検出（存在しない問題の指摘）がないか

### 3. フィードバックの質

- 命令形ではなく問いかけ形式になっているか
- 具体的な観察事実に基づいているか
- チームの自律性を尊重しているか

### 4. 改善提案の実用性

- 実行可能で具体的か
- チームが自分で考えるための問いがあるか

## イベント別：期待される検出項目

### Daily Scrum

- [ ] タイムボックス超過（15分以上）
- [ ] 報告会形式になっている
- [ ] スプリントゴールへの言及不足
- [ ] 技術議論の Daily 外切り出し不足
- [ ] 沈黙メンバーへの配慮不足
- [ ] スコープ変更の割り込み
- [ ] SM のファシリテーション不足

### Sprint Retrospective

- [ ] 前回 Try 振り返りの欠如
- [ ] 個人攻撃の発生
- [ ] 心理的安全性の問題
- [ ] 改善案の抽象性（「もっと頑張る」等）
- [ ] アクション担当者・期限の欠如
- [ ] タイムボックスの問題

## プロンプト改善サイクル

1. **初回テスト** — 実際の議事録で基本動作確認
2. **問題特定** — 検出漏れ・誤検出を特定
3. **プロンプト調整** — [CLAUDE.md](CLAUDE.md) のチェックリストを改善
4. **再テスト** — 改善効果を確認
5. **繰り返し** — 品質が安定するまで

改善の判断基準：

| 状況 | 対応 |
| --- | --- |
| 検出漏れが多い | CLAUDE.md のチェックリスト強化 |
| 過検出が多い | 判定条件の厳格化 |
| 特定イベントで弱い | Specialist Agent の分離を検討 |

---

## 既知の制限事項

- 議事録の形式によって検出精度が変わる可能性
- 非常に長い議事録では重要な点を見落とす可能性
- 文化的コンテキスト（日本の SI 業界特有の慣習等）の理解に限界
